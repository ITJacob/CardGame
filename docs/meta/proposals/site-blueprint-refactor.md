# site 端「玩法蓝图」重构设计稿

> 状态：已拍板 · 2026-10-22（四项决定见 §11）
> 范围：`site/`（技能池数据站），外加 `docs/tools/blueprint_score.py` 的产物扩展
> 不改：`docs/json/`（技能池权威源）、`docs/meta/rounds/*.md`（蓝图声明正源）、`docs/ddd/`
> 一句话：把「玩法蓝图」从一份只有脚本读的 md，变成站点的一等公民——**每个途径一页蓝图**，让「声明 → 实证 → 兑现」三层在一屏内对得起来。

---

## 0. 一页结论

1. **新增一个顶层入口「玩法蓝图」**（`#/blueprint`），并给 22 个途径各一页 `#/blueprint/<pid>`。这是本次重构的主产物，不是给「设计评分」加一个 tab。
2. **新增一个生成产物 `docs/analysis/blueprints.json`**，由 `blueprint_score.py` 在现有产物之外一并写出；前端只读、不解析 md、不重算 rubric。
3. 页面按「声明 / 实证 / 兑现」三层组织：蓝图说它要做什么 → 卡池实际做了什么 → 两者对账差在哪。**任何一层都不覆盖另一层**。
4. 在四个既有页面开接口：卡片列表（角色筛选 + 角色徽章）、卡片详情（蓝图定位块）、设计评分（角色分布 + 蓝图反链）、统计分析（卡角色维）。
5. 蓝图评分 **95–100 压缩带**，是工序门槛（≥60 方可进格③），不是排行榜；站点不按它排序、不做「蓝图得分榜」的暗示。

## 1. 背景：这一批提交改了什么

2026-10-19 ~ 10-22 的蓝图批次（`46221d5` 起，至 `baa8793`）把「机制期玩法轨」的声明层落地了：

| 落点 | 内容 | 站点现状 |
|---|---|---|
| `docs/meta/rounds/<pid>.md` | 22 途径各一段 `## 玩法蓝图`：命题 / 风格边界 / 轴玩法 / 跨轴钩子 / 跨系钩子 / 角色配比 | **完全不读**（全站 0 处引用「蓝图」） |
| `docs/tools/blueprint_score.py` | rubric 七维 0–100；产出 `blueprint_score.md` + `blueprint_fulfillment.{md,json}` | 不消费 |
| `docs/json/*.skills.json` | 卡新增 `role`（core/starter/bridge/generic/trap/tech，21/22 途径已回填）；轴新增 `anchor` | `role` 只用于「旗舰」徽章，其余不显示 |
| `docs/analysis/scores.json` | 2.14 起轴级三维改为「锚点兑现 / 产层兑现 / 收束兑现」，并带 `roleDist`、`legacyDims` | 评分页已同步 2.14 轴维；但 `roleDist` 未渲染、蓝图无入口 |
| `docs/meta/SCORING.md` | 2.12 角色口径、2.14 兑现重切 | 站点只在评分页体现部分结果 |

结论：**评分页的「分数」是新版，站点的「内容组织」还是旧版。** 旧版把途径理解成「卡 + 轴 + 评分」，新版把途径理解成「蓝图（声明）→ 轴（玩法循环）→ 卡（实证）→ 兑现（对账）」。站点缺的是中间那根脊椎。

### 1.1 为什么「加一个页面」不够

蓝图不是又一份统计报告，它同时是：

- **设计工序的输入**：计划卡数、角色配比、签名键承诺、决策点，是格③逐卡设计稿的约束；
- **评分口径的正源**：2.14 的轴级三维已经改成「蓝图声明 ∩ 卡池实证」；
- **下一轮的待办清单**：兑现缺口（如 hunter 的 role 未回填、若干签名键只有 1 张实证）就是迭代输入。

如果只做一张只读表，站点仍然回答不了三个最常问的问题：

1. 这个途径到底想让玩家干什么？（命题 / 决策点）
2. 它说要做的事，卡池做到了几成？（兑现率）
3. 差的那几成具体是哪张卡、哪个钩子、哪个角色？（可点击的缺口）

所以重构的核心是**把「蓝图 — 轴 — 卡」做成可互跳的对象图**，而不是多一个文档页。

## 2. 设计原则

1. **声明正源与实证正源不合并**。蓝图 md 是声明，`score.py` 是实证；站点只做对账展示。任何「站点看起来像新数据」的字段都必须标出来源。
2. **三层对照**。每个途径页固定三段：声明（蓝图）、实证（卡池/轴）、兑现（对账）。缺一层就空着并说明，不拿另一层补。
3. **前端不重算**。沿用 `scores.json` 先例：rubric、兑现率、角色计数全部由 Python 预计算，前端只展示。理由不只是性能——解析规则（中文表头、`→` 分段、占位串、卡名词典匹配）已经在 `blueprint_parse.py` 里演化过一轮，JS 再实现一份必然漂移。
4. **蓝图分是门槛，不是名次**。22 途径 95–100，排序没有信息量。总览默认按 manifest 途径序（与统计热图行序一致），可选排序里也不给「蓝图分」。
5. **证据可点击**。蓝图表里的卡位 → 卡详情；锚点状态 → 状态浮层/详情；枢纽状态 → 状态；参与途径 → 该途径蓝图页。点不动的名字等于没写。
6. **占位不是错误**。「（待补强1卡）」「（待他途径补读取卡）」是设计阶段的合法占位，渲染成虚线「待补」芯片，不标红、不链空。
7. **渐进增强**。蓝图 JSON 缺失 / 某途径未建蓝图 / role 未回填时，既有页面原样工作，新页面给出明确降级说明。

## 4. 数据契约

### 4.1 为什么是生成 JSON，而不是前端解析 md

| 方案 | 判定 |
|---|---|
| A. 前端 fetch 22 份 `rounds/*.md`，JS 移植 `blueprint_parse.py` | ✗ 解析规则（中文表头逐字匹配、节标题同行表头、`→` 分段、卡名长优先匹配、占位串）要在两处维护；规则一变站点静默错位。且 22 请求 + 前端还要自己做 role/兑现 join |
| B. 前端只 fetch `blueprint_fulfillment.json`，蓝图正文仍只读 md | ✗ 兑现率页面有了，但命题/轴玩法/钩子仍然不可读，重构目标没达成 |
| **C. `blueprint_score.py` 增写 `docs/analysis/blueprints.json`（推荐）** | ✓ 单一解析源；一次请求；所有 join（卡 id、实际 role、锚点对账、兑现 ok）在 Python 侧完成；与 `scores.json` 的消费模式完全一致 |

选 C。它只是把脚本已经算出来的东西**多写一份机读面**，不新增权威源：`rounds/*.md` 仍是声明正源，`blueprints.json` 是派生产物（头注释「勿手改」）。

### 4.2 生成器改动

`docs/tools/blueprint_score.py` 新增 `write_blueprints_json(...)`，与现有两个产物同轮写出：

```
docs/analysis/blueprints.json         ← 新增，站点消费
docs/analysis/blueprint_score.md       ← 保留，人读榜
docs/analysis/blueprint_fulfillment.md ← 保留，人读对账
docs/analysis/blueprint_fulfillment.json ← 保留，机读对账（不删，兼容）
```

`build_analysis.py` 已经按序调用 `blueprint_score.py`，只需把新文件加进结尾提示与 `WORKFLOW.md` 产物表。**不新增 STEPS。**

生成器要补的 join（现在 `reconcile()` 里已有大部分，只是没落 JSON）：

| 字段 | 来源 |
|---|---|
| 蓝图七维得分 / 失分项 | `score_blueprint()` 返回值 |
| 命题 / 风格边界 / 钩子 / 角色配比表 | `parse_blueprint()` 的 `sections` |
| 轴锚点 / 计划卡数 / 签名键承诺 | `轴玩法` 各行 |
| 产出段 E* / 消费段 P* | `parse_pc_chain()`（卡名词典匹配） |
| 卡位 → 卡 id | `pathways[pid].cards` 名称索引；占位串保留原文 |
| 锚点是否兑现 | `axes[axis].anchor` 对账 |
| enabler / payoff 实证 | 复用 `score.py` 的轴级结果 |
| 签名键实证数 | `score.signature_counts()` |
| 角色声明 vs 实际 | 蓝图「角色配比」表 vs `cards[].role` |
| 跨轴 / 跨系钩子逐行 ok | 扩展 `reconcile()`，现在只汇总 miss |

### 4.4 加载与缓存

- `data.js` 新增 `loadBlueprints()`：懒加载 + 内存缓存，`fetch(..., { cache: 'no-cache' })`，与 `loadScores()` 同款。只有蓝图路由、以及需要反查的卡片页会调。
- **不加入 SW 的 `DATA_RE`**。`docs/analysis/*.json` 目前就不在 SW 缓存白名单里（`scores.json` 同样），刷新即所见；蓝图 md 改完重跑脚本后，站点刷新立刻拿到新 JSON。若以后要离线可用，再单独评估，别顺手塞进 SWR。
- 失败态：页面顶部一条 `panel` 说明「blueprints.json 未生成 / 加载失败」，给出命令 `python docs/tools/build_analysis.py`，其余页面不受影响。

## 5. 页面设计

### 5.1 玩法蓝图总览 `#/blueprint`

```
玩法蓝图
22 途径 · 全部回溯补登 · 数据生成 2026-10-22 · 口径 WORKFLOW.md「玩法蓝图」

[全部 22] [有兑现缺口 14] [角色未回填 1]        排序 [途径序 ▾] [设计分↑] [兑现缺口↓]

┌────────┬──────┬──────┬────────┬─────────────────────────────┬──────┬────────────┐
│ 途径   │ 蓝图 │ 状态 │ 设计分 │ 兑现（锚点/签名/角色/跨轴/跨系） │ 卡数 │ 备注       │
├────────┼──────┼──────┼────────┼─────────────────────────────┼──────┼────────────┤
│ 猎人   │  96  │回溯  │  55.0  │ ▓▓▓░ 4/4 1/3 1/7 0/3 1/2     │  43  │ role 未回填 │
│ 药师   │ 100  │回溯  │  63.2  │ ▓▓▓▓ 4/4 3/3 7/7 3/3 1/1     │  40  │            │
│ 战士   │  97  │回溯  │  71.1  │ ▓▓▓▓ 4/4 3/3 7/7 2/2 —       │  33  │            │
└────────┴──────┴──────┴────────┴─────────────────────────────┴──────┴────────────┘

行点击 → #/blueprint/<pid>
「设计分」列 → #/score/<pid>（阻止冒泡）
```

设计要点：

- 行序默认 **manifest 途径序**，与统计热图 22 行、卡片列表途径序一致。排序只是可选读法，不改变默认。
- 「兑现」列是五个**分段小条**（锚点 / 签名键 / 角色配比 / 跨轴钩子 / 跨系钩子），每段 `hit/total`，悬停给 miss 明细。整列不合成一个百分比——五类缺口的性质不同，合成会把「role 未回填」和「一个枢纽没读者」抹平。
- 蓝图分只作为一列，不加排序入口；页头写清「≥60 为工序门槛，不当排行榜」。
- 筛选「有兑现缺口」= 任一项 `hit < total`；「角色未回填」= `roleDist` 为空（当前仅 hunter）。
- 空态：未建蓝图的途径单独一行灰色「未建蓝图」，不链入空页（当前 0 条，但新途径会先有卡后补蓝图）。

### 5.2 单途径蓝图页 `#/blueprint/<pid>`

这是本次重构的核心页面。自上而下：

```
┌ 途径色带 ────────────────────────────────────────────────────────────┐
│ 🗡️ 战士 warrior            蓝图 97/100 · 回溯补登 · 2026-10-21          │
│ [设计评分 71.1 →]  [卡片 33 张 →]  [统计分析 →]                          │
└──────────────────────────────────────────────────────────────────────┘
```

#### ① 命题（hero）

```
┌ 命题 ────────────────────────────────────────────────────────────────┐
│ 宣判将死之人——战士在局内主动改写「场上谁是那个被宣判的将死之人」          │
│                                                                      │
│ 可操作变量                          代价 / 输面                        │
│ 宣判对象与时机、斩杀窗口内的集火编排    限期未斩则标记撤销+护盾+自伤+不可再宣判 │
└──────────────────────────────────────────────────────────────────────┘
```

一句话命题用大号字（16–18px），下面两栏。命题是蓝图的「目标函数」，放在最前，不折。

#### ② 风格边界

三格横排（窄屏纵排）：

```
主签名维度                          使用的全局通用机制           红线来源
守护黄昏（elem:holy 圣光 + …）        [武器][召唤][治疗][驱散]      「零吟唱——武技全部瞬发……」
```

- 机制用 chip；词表外的机制不标错，只换中性样式（设计侧已由 `GLOBAL_MECHANISMS` 校验）。
- 红线来源是引用句，用 `blockquote` 样式，右上角不挂「查看身份卡」外链（文档在仓库里，站点没有独立身份卡页；避免给一个半成品入口）。

#### ③ 轴玩法（4 张轴卡）

每轴一张，桌面两列、窄屏单列：

```
┌ 🗡️ 武艺 martial ─────────────────────────────────────────────────────┐
│ 锚点 equipment:weapon  ·  计划 11 张 / 实际 12 张  ·  轴分 77.6        │
│                                                                      │
│  产出 ──────────────→ 消费 ──────────────→ 清除                       │
│  银白细剑 / 黄昏巨剑 /    无坚不摧 / 神罚 /     武器被缴或耐久耗尽        │
│  兵械通晓                 武器大师                                    │
│  （3 张可点）             （3 张可点）                                 │
│                                                                      │
│ 玩家决策点：武器槽投资与耐久节奏——装哪把、普攻耗到哪档再补              │
│                                                                      │
│ 签名键承诺  elem:holy ✓3  破甲重击 · 晨曦领域 · 光之风暴                │
│ 角色配比    声明 core×6 starter×2 trap×1 generic×2                    │
│             实际 core×7 starter×1 trap×1 generic×3                    │
└──────────────────────────────────────────────────────────────────────┘
```

- **产出→消费→清除** 是一根三段箭头（不是三行表格）：左段 = `parse_pc_chain` 的 E*，中段 = P*，右段是清除叙述文本。清除段本来就不解析卡名，不能做成同样的卡位列表。
- 锚点 `kind:id` 按 kind 渲染：`status` 用 `statusSpan`（状态浮层）、`resource`/`primitive`/`element`/`trigger` 走词典 `termSpan`、`equipment`/`channel`/`rule_slot`/`geometry`/`action_control` 等用「中文 kind 名 + mono id」；查不到就裸 mono，不标红。
- 签名键 chip：键 + 实证数（✓ = ≥2 卡）；承诺卡位可点，占位串（`（待补强1卡）`）渲染为虚线「待补」。未承诺的键不出现在这里（2.14 起「承诺即正源」）。
- 计划/实际卡数不等时，数字用 `warn` 色但不说「错」——计划是设计输入，实际可能因增删卡漂移，兑现率页会给结论。
- 角色配比两行（声明/实际），用 6 段堆叠条 + 数字；`generic ≤25%`、`trap ≤20%` 上限只在校验越界时显示提示（蓝图层 rubric 已管）。

#### ④ 跨轴钩子 / 跨系钩子

两张表，逐行带兑现标记：

```
跨轴钩子（2/2 兑现）
┌──────────┬──────────┬───────┬───────┬──────────────────────────────┐
│ 卡位      │ 读轴      │ 概念   │ facet │ 用途                         │
├──────────┼──────────┼───────┼───────┼──────────────────────────────┤
│ 黄昏巨剑 →│ 黄昏 twilight │ status │ read  │ 读衰老层数定巨剑黄昏加成   ✓ │
└──────────┴──────────┴───────┴───────┴──────────────────────────────┘

跨系钩子（显式声明无）
  本途径不写跨系枢纽：doom_mark 私有化，避免跨途径污染（设计本意，非缺口）
```

- 卡位 → 卡详情；读轴 → 该轴在本页的高亮定位（`?axis=twilight`）；facet 用 mono；`✓/✗` 带 title 说明 miss 原因。
- 跨系钩子的「枢纽状态」→ `statusSpan`；participants → 各途径蓝图页链接。显式声明无时渲染中性说明，**不要**出现空表头或「缺失」。
- 未兑现行用左侧 `warn` 竖线 + 行尾「✗ 未兑现」，并显示 miss 原因（如「写入卡为占位」「hub 未标 crossPathway」）。

### 6.3 语义编码

- **声明**：虚线边框 + 「声明」小字；**实际**：实线/实底。两列并排，不靠颜色区分。
- **兑现**：`✓`（ok）、`✗`（有 miss）、`—`（显式声明无）；`✗` 必须同时带文字原因。
- **角色颜色**（辅助，不做唯一编码）：
  `core → --accent`、`starter → --uncommon`、`bridge → --rare`、
  `generic → --dim`、`trap → --warn`、`tech → --epic`、`flagship → --legendary`。
  全部带中文角色名，色弱用户靠文本可读。
- 不引入新的全局语义色；缺口一律 `--warn`，错误/加载失败才 `--bad`。

### 6.4 响应式

- 断点沿用 768 / 640：轴卡两列 → 单列；命题两栏 → 单栏；兑现表横向滚动（保留首列 sticky，同热图）。
- 页内小节导航在 ≤640 横向滚动，不换行堆高。
- 22 行总览表在窄屏保留「途径 / 兑现 / 设计分」三列，其余列折进展开行（与热图列折叠同一思路，但用 `<details>` 行展开，不写死 nth-child）。

## 7. 交互细节

1. **深链**：
   - `#/blueprint/<pid>` 直达途径页；
   - `#/blueprint/<pid>?axis=martial` 滚动到该轴并短暂高亮（`route()` 已支持 query 串）；
   - `#/cards?pathway=warrior&role=core` 直达角色筛选；
   - `#/score/<pid>` 与蓝图页双向互链。
2. **锚点**：
   - `status:xxx` → 复用状态悬停（deferred 状态就绪前显示 id，就绪后页面刷新一次，沿用评分页 `onStatusesReady` 模式）；
   - `equipment:weapon` 这类没有状态定义的锚点 → 「装备槽 · weapon」+ 不挂空浮层；
   - `channel:phase` → 词典 `channel` 栏目（若无词条，裸 mono）。
3. **卡位**：卡名 → `#/card/<id>`；占位 → 不可点、`title` 说明这是设计占位。
4. **表格行**：跨轴/跨系行整行不点击（避免误触），只让名字可点；兑现标记 hover 显示 miss 原因。
5. **键盘/触屏**：角色 chip、轴卡折叠用原生 `<details>` / `<a>`；不自定义 tab 组件。触屏浮层沿用 `tooltip.js` 的居中分支。
6. **打印/复制**：蓝图页头提供「复制本页要点」按钮（可选 P3），输出 plain text 命题 + 四轴决策点，方便带进设计会话。

## 8. 降级与边界

| 情况 | 表现 |
|---|---|
| `blueprints.json` 404 / 解析失败 | 页面级提示 + 生成命令；导航仍可用，其他页不受影响 |
| 某途径无蓝图 | 总览灰行「未建蓝图」；`#/blueprint/<pid>` 显示说明，不渲染空轴卡 |
| `role` 未回填（hunter） | 角色区显示「role 尚未回填」+ 蓝图声明配比；不画 0 条 |
| 卡位是占位串（`（待补强1卡）` 等） | 虚线「待补」chip，不链空；兑现率照实计 miss |
| 钩子显式声明无 | 中性说明「显式声明无」；兑现项显示 `0/0` 而不是 `0%` 红条 |
| 锚点查不到 status / 词典缺词条 | 裸 mono，不标「未收录」红字（与 `defSpan` 同一条纪律） |
| 计划卡数 ≠ 实际卡数 | 数字 `warn` 色 + 「计划 / 实际」标签；不阻断 |
| 蓝图 md 已改、JSON 未重跑 | 页头生成日期 + 一句「数据由 build_analysis 生成」，避免误以为站点是正源 |
| 评分 JSON 与蓝图 JSON 版本不一致 | 两个文件各自带 `generated`；同日不同轮时在页头并排显示，不下结论 |
