# 工作流：从设定到技能质量分析

> 本文件定义当前 AI 协作产出的标准流水线。各环节产物归属见 CLAUDE.md 文档地图。

## 流水线总览

```
① 设定补全        ② 机制落地         ③ 技能结构化       ④ 质量分析
诡秘之主资料库/ →  ddd/（权威正源）→  json/          →  analysis/
（故事背景/源素材）  （战斗机制 DDD）   （技能池 JSON）    （统计 + 总览）
                                                        ↓
                       ⑤ 重设计迭代 ←──────────────────┘
                                                        ↓ 平台期 / 无可操作变量 / 人工发起
                       ⑥ 骨架重议 ──→ 机制扩容回 ②；整途径重构回 ③→⑤（重构模式）
```

> 2026-09-18 起技能稿 md 环节取消：文字稿已完成历史使命（差集信息已回收进 JSON），归档为只读快照 `docs/archive/skill-design_v0.3/`，技能内容唯一维护面 = `docs/json/`。

流程规范与生成约束集中在 `docs/meta/`，全部脚本在 `docs/tools/`。

**依赖方向**：①→②→③→④ 单向推进。唯一允许的反向流动是 **③→②**：JSON 落地时发现 ddd 语义缺口（如 snapshot / modify_damage 原语），先拍板补定义再回写 JSON，拍板结论登记到 `GENERATION_BRIEF.md` §14。

## 环节⑤：逐职业重设计推进（2026-09-26 建立）

```
score.py 评分 → 取总览榜尾途径 → 读计分卡失分项（scorecard.md / 网页评分页）
  → 设计修改（SCORING 2.0 优先序：补「收束」——payoff 读 / 通道下游 / def 内闭环 → 补身份机制 → 提多样性/连通/差异化）
  → 四脚本 + lint 门禁 → 重跑 score.py 确认涨分 → commit → REDESIGN_LOG（现归档于 `docs/archive/meta/`）记一行
```

- **节奏**：一途径一迭代，一次会话 1–2 个途径；不跨途径批量改（失分归因会糊）。
- **风格驱动**（2026-10-01 差异化专项起，已收官）：立项优先序前置「签名键空白/发芽」——每途径身份卡（原著锚/签名键/红线/差距）见 `途径设计身份.md`；推进规则与 11 批排队表见 `docs/archive/meta/差异化重构计划.md`；风格迭代轮验收加一条：「差异化」维（SCORING 2.0，25 分）只增不减。
- **无 payoff 轴**不再靠 `payoffVacuumAccepted` 逃生舱（SCORING 2.0 已废其计分效力）：改按「间接收束（通道下游读者）/ def 内闭环」自动计分——自闭环型（身份 def 自带 triggers/阈值/静态载荷）是合法形状，不缺分。
- score.py 只读、随时可跑：它进门禁但不阻塞——防「越改越差」无感知。
- 评分只评**结构与设计丰富度**，不治数值；数值标定属平衡期，另开工。
- **重构模式（2026-10-23，由环节⑥进入）**：不走总分取榜，按骨架拍板排期；蓝图命题整条重写（不是补卡），
  验收 = 蓝图重写 + `blueprint_fulfillment.md` 对账 + 玩法轨 `playable_scan.py` 从「无可操作变量」转「有可操作变量」；
  一途径一 commit，REDESIGN_LOG 记骨架变更（改前/改后命题）。

## 环节⑥：骨架重议（2026-10-23 立）

**为什么需要**：环节⑤按分数取榜，只能在既有骨架内改卡；评分与指纹测得到「怎么实现」，测不到「玩什么」。
22 条蓝图命题实测已塌成 5 个骨架（见 `骨架重议.md`：A 前置门槛 7 / B 累积-择时兑现 6 / C 规则收租 3 /
D 自反代价 2 / E 编排顺序 3，A+B ≈ 59%；sleepless 独立）。2×2 矩阵的「引入全新变量（最贵）」格此前
没有流程会走到——本环节就是那一格的执行入口。

**触发**（任一）：

1. 全库回溯或差异化迭代进入平台期（连续两轮总分 / 距离无实质变化）；
2. `playable_scan.py` 2×2 体检把某途径判入「无可操作变量」格（升级路径）；
3. 主人人工发起。

**流程**：

1. **撞车簇确认**（主人裁定哪些是真撞车；共享输面不算，只共享通货措辞要裁）；
2. **每簇 AI 出 3 个候选新骨架**，不得代拍；每个候选写一句话命题 + 可操作变量 + 变量代价/输面；
3. 每候选标**机制支撑三档**：已有 / 需扩展 / 需新建；需扩展或新建的写影响面与 MVP；
4. **机制扩容走 ② 机制落地**：提案 → 拍板 → ddd/params → schema → 数据；
5. 拍板后排期，进 ⑤ **重构模式**（整途径重构，不按分取榜）。

**Gate（六条，全过才可动 ③）**：

1. 命题三格齐、可操作变量 ≥1（沿用蓝图命题表）；
2. 至少 2 个旧机制被转移或退役——做转移不做加法（机制期第 10 项）；
3. 机制提案含影响面审计与迁移选项（兼容 / 零迁移 / 整批，逐机制评估）；
4. 声明可对账：新变量落地后须 ≥2 卡写、≥1 卡读，`playable_scan` 由「无变量」转「有变量」；
5. 主人格④独拍（命题落法、新机制、所有权分叉、卡数、代价形式）；
6. 未过 Gate 不得改 ③ 卡池；过了也只是一途径一 commit。

> 与七格推进的关系：格② 2×2 的「无可操作变量」格升级到本环节；本环节的输出回到格① 重写命题与蓝图。

### 机制扩容提案模板

放 `docs/meta/proposals/<机制名>.md`，九节：

1. **一页结论**：推荐方案 / 它让哪些新决策成为可能 / 没有它会卡住哪些骨架；
2. **设定核查**：原著依据与边界（先定能做什么、不能做什么）；
3. **现状与问题**：现在的实现方式、为什么不够；
4. **模型方案对比**：2–3 案，逐项比归属上下文 / 三件套形状 / 与现有概念关系 / 成本；
5. **推荐模型**：Def→Grant→Instance 形状、归属上下文、生命周期；
6. **原语与谓词**：新增 / 修改清单；新原语须先在 `docs/meta/SCHEMA.md` §5.2 登记再改 schema；
7. **所有权**：全局概念还是途径私有；轴只能声明 facet（SCORING §二·三）；
8. **影响面审计 + 迁移**：卡 / 状态 / 谓词 / schema / validate / score / site 逐项计数与迁移选项；
9. **解锁骨架 + MVP + 拍板项**：≥2 个骨架候选、最小可行切片、不可逆项清单。

## 机制期玩法轨工作流（2026-10-19 立）

> 背景：评分体系测的是「卡片长什么样」，与「玩家干什么」正交（卡级最近对与途径间距离相关仅 0.135）。
> 机制期改为**命题驱动**：人定目标函数，AI 数数与查表。

### 三条元规则（每次设计/审核必过）

1. **可感知性检验**——看得见吗？能预判吗？**会改行为吗？**（第三问是终极判据：玩家不会为躲开它而改变出牌，就是名义值。）
2. **成对检查四问**——谁写它？谁读它？**谁清它、有几种清除路径？每种清除路径各自触发什么？**
3. **结果不挂手段**——成功/失败的判定必须挂在「结果」上（目标死没死），不能挂在「手段」上（用了哪张卡）；须列出**还有哪些别的手段能达成同一结果**。

### 第 10 项：做转移不做加法

凡引入新决策（登记/切换/消耗/取舍），必须同时削弱「不做这个决策」的基线强度，把强度迁进「做了」的分支。三条防刷约束：

1. 条件必须**玩家可能达不成**（自动满足的条件 = 伪装成转移的常驻 buff）；
2. 转移不能过头（纯转移卡 ≤ 途径卡数 1/3，其余保留基础段）；
3. 新卡无基线可削弱 ⇒ 等价于「必须有代价」，显式指向逐卡第 ⑤ 问。

机制期只做**结构性转移**（无条件 → 条件触发）；数值性转移归平衡期。

### 2×2 诊断矩阵（格②体检输出）

| | 有集火 | 无集火 |
|---|---|---|
| **有可操作变量** | 理想态 | 加「标记稀缺性」（中） |
| **无可操作变量** | 补 1 张写入卡（最便宜） | 引入全新变量（最贵） |

途径排序用本矩阵，**不用分数升序**——分数会把「双挂」和「只差一张卡」混在一起。

> 「无集火 / 无可操作变量」格与「引入全新变量（最贵）」格不再就地补卡：前者进环节⑤常规迭代，
> 后者**升级到环节⑥骨架重议**（2026-10-23 起；见上文 Gate 与提案模板）。

### 七格推进（一途径一轮）

① **命题 + 玩法蓝图（主人拍）**：一句话玩法命题 + 可操作变量 ≥1，写入 `rounds/<途径>.md`；
途径首轮须先立**玩法蓝图**（途径级一次性产物，见下节），七格推进是蓝图之下的迭代轮。AI 只出 3 候选，不得代拍。
② **体检（AI）**：`python docs/tools/playable_scan.py` 出 6 项指标 + 2×2 分类。
②→③ **蓝图 Gate**：`python docs/tools/blueprint_score.py` 蓝图评分 **≥60** 方可进格③
（不足则由主人显式豁免并记入 rounds 文件）；蓝图的计划卡数/角色配比/签名键承诺是格③逐卡设计稿的输入。
③ **设计稿（AI 出 / 主人审）**：逐卡四列表（id / 保留·改写·新建·删除 / 新动作 / 玩家在这里决定什么），
逐卡标 `role`（六值口径见 SCORING §一·附），与蓝图角色配比/计划卡数对账。
被动卡第 4 列须写「它让哪张主动卡多了一个决策维度」；只写「打谁 / 有能量就打」不算。
④ **拍板（主人独拍）**：不可逆项（命题落法、新机制、所有权分叉、卡数、代价形式）。
⑤ **落地（AI）**：先 statuses → 手写核心卡 → 批量引擎处理纯形状卡 → 三道人工工序（describe 重写 / note 分栏 / 抽样人读 10 张）→ 四门禁。
⑥ **验收（双轨）**：形状轨（四门禁全绿 + 总分不退化 + 蓝图兑现率对账 `blueprint_fulfillment.md`）
+ 玩法轨（`playable_scan.py` 10 项，**永不进 score.py 的 100 分**；蓝图评分同样永不进 100 分）。
⑦ **复盘（主人）**：必答「这轮玩家多了一个什么决定？」答不出 ⇒ 机械轮 +1；连续 2 个机械轮 ⇒ 停工改流程。

### 玩法蓝图（途径级一次性产物，2026-10-21 立）

蓝图回答「途径基础风格 + 轴作为细化玩法承接了哪几种机制」，在设计阶段定玩法、再补卡的细节设计
（入门卡/过渡卡/通用卡按角色配比补齐），不再等卡全部设计完再补救分数。
载体 = `docs/meta/rounds/<途径>.md` 前置章，评分器 = `docs/tools/blueprint_score.py`（rubric 0–100：
命题 10 / 风格边界 15 / 轴循环 25 / 决策点 10 / 签名键 15 / 角色配比 15 / 钩子 10）。

**章格式（固定表头，机读逐字匹配）**：

```markdown
## 玩法蓝图（<草案|已拍板|回溯补登> · <日期> · 蓝图评分 <xx>/100）

### 命题
| 一句话命题 | 可操作变量 | 变量代价/输面 |

### 风格边界
| 主签名维度 | 使用的全局通用机制 | 红线来源 |

### 轴玩法
| 轴 | 名称 | 锚点(kind:id) | 产出→消费→清除 | 玩家决策点 | 签名键承诺(键:卡位) | 计划卡数 | 角色配比 |

### 跨轴钩子
| 卡位 | 读轴 | 概念 | facet | 用途 |

### 跨系钩子
| 枢纽状态 | 写入卡位 | 读取卡位 | participants |

### 角色配比
| 角色 | 张数 | 卡位 |
```

**机读约定**：只认 `## 玩法蓝图` 之下各 `###` 节的管道表格（表头可写在节标题同行或次行）；
单元格内列表用半角逗号、禁 `|` 与换行；签名键承诺写 `键:卡位,卡位;键:卡位`（分号隔键）；
轴角色配比列写 `core×2,generic×1`；角色配比表逐角色一行，可加 `flagship` 行（卡位须 ⊆ core∪trap，恰 4 张）；
跨轴/跨系钩子允许「显式声明无」（只一行且首格为「无」）；下一个 `##` 即蓝图章结束。

**对账来源**：主签名维度 ↔ `途径设计身份.md` §一；签名键 ↔ score.py `PATHWAY_SIGNATURES`；
锚点 kind ↔ SCORING §二·零 14 枚举；facet ↔ SCORING §二·三 词表；角色 ↔ SCORING §一·附 六值；
全局通用机制 ↔ blueprint_score.py `GLOBAL_MECHANISMS` 词表（声明「占用 vs 通用」，使途径不把全游戏通用玩法写死包揽）。

### 全库回溯计划（2026-10-21 立）

存量 22 途径全部回溯补蓝图 + 回填 role。机器预填用 `docs/tools/prefill_blueprint.py`，
命题与决策点必须人写。顺序按 scorecard 总分升序（榜尾正是环节⑤下一批重设计对象），
已审的 sleepless/warrior 放最后（刚走完机制期迭代，回溯成本最低）。一批会话 3–4 条，
一途径一 commit（`docs(rounds): XX玩法蓝图回溯 + role 回填`）：

1. hunter → apothecary → reader → sailor
2. spectator → pryer → criminal → apprentice
3. thief → corpse_collector → assassin → savant
4. lawyer → seer → arbiter → planter
5. monster → chanter → supplicant → prisoner
6. sleepless → warrior（已审末批，命题可从既有 rounds 首段回收）

**三条铁律**：格④裁定数 = 0 ⇒ 整轮作废；格③ 0 行被打回 ⇒ 判「没真审」；玩法轨指标永不进 100 分（进则两轮内被爬山）。

## 分析与评分工作流（2026-09-30 整合）

评分（score.py）与统计（build_* ×4）同源同面：全部只读 JSON、产物全部落 `docs/analysis/`、全部勿手改。
**统一入口**：`python docs/tools/build_analysis.py`——依次跑 score + 四个 build 脚本，任一失败非零退出。

**何时跑**：`docs/json/` 任何变更（改卡 / 改轴元数据 / 改状态），四门禁 + lint 全绿后**同轮**跑本入口，
产物与 JSON 变更进同一 commit——网页评分页与计分卡永远与 JSON 同代。数值标定期（下一批）改 JSON 后同样走本流程，时效性由「同轮 commit」保证。

**产物清单与消费**：

| 产物 | 生成者 | 消费 |
|---|---|---|
| `scorecard.md` | score.py | 人读计分卡（环节⑤取榜与失分归因的唯一依据；⚠单维 标记进人工裁定队列） |
