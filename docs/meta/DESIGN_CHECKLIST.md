## 设计一张技能卡：8 步

| # | 维度 | 决策内容 / 约束来源 |
|---|---|---|
| 1 | **定位** | 落在哪个途径、哪个构筑轴；在轴里当产层（enabler）还是读层（payoff）——决定它在轴评分里的角色（SCORING.md 轴六维） |
| 2 | **卡面骨架** | `kind` 主动/被动；被动挂 `hook`（触发点 15 个封闭集）；`sequence` + 序列名；`rarity`（rarityMap 由序列位定死，不可自选）；是否旗舰（flagship，理想 4 张/途径） |
| 3 | **效果 AST** | `op` 结构（sequence / if / repeat…）+ 原语组合（30 个封闭集，schema `effect.oneOf` 为权威源）+ 参数（元素/属性/资源/锚点/条件谓词，全部走值域 + glossary 词典）——技能真正的设计主体。攻击行为先想清目标规格：**先定 `mode`（unit=指定单位 / area=坐标区块，后者即 AoE）**，再定缺省基准 = `mode:unit + 敌方同路最前排`（同路排首；enemy_front 语义、scope 回退、溅射时点见 `ddd/params/共享内核参数.md` §一，brief §1.6），偏离缺省要在卡面写明 targetSpec |
| 4 | **硬约束自检** | 触发点封闭、R1–R6 随机治理（chance 须登记 + 单次抽样 + 只用于非伤害维）、G8 位移约束、数值锚点（≈3能量 ≈6伤害 ≈10%最大生命，brief §1–§3）——只校结构与锚点带内，不校具体大小 |
| 5 | **文本三件套** | `describe`（机器可读复述）/ `flavor` / `lore`，缺一扣「文本完备」分 |
| 6 | **附属定义块**（按需） | 卡面内嵌 `unitDefs` / `zoneDef` / `domainDef` / `upgradeLadder` / `variants`；界域/区域 def 与 grant 字段成对（`domainDef`↔`domain`、`zoneDef`↔`zone`）。新状态不落卡面，写 `<途径>.statuses.json`（跨途径共用进 `common.statuses.json`），卡面用 mount_status 的 statusId 引用 |
| 7 | **元数据收尾** | `conversionNotes`（稿面意图）、`frameworkFlags`（用到的机制缺口登记 landed 状态）、`tentative`、`art` |
| 8 | **过门禁** | 四脚本全绿（validate / validate_schema / check_enum_sync / check_glossary）+ validate 的稀有度与不变量校验 |

## 设计一个状态：7 步

statusDef 38 个字段，设计决策收敛为七组：

| # | 维度 | 决策内容 |
|---|---|---|
| 1 | **身份** | `id` / `name` / `note` + `category` 分类（buff / debuff / 控制…词典值域）——网页统计分析页「状态定义面」分类 × 原语热图的第一个轴 |
| 2 | **时长模型** | 四件套怎么取：`duration`（配 `durationUnit`：缺省 `tick` 自然到期 / `self_turn` 按持有者行动机会数）/ `maxStacks`（叠层）/ `charges`（次数）/ `dispelable`——决定「层数语义」，也是评分「身份锚定」查的层数引擎。**次数消耗型 / 出手自破型一律 `self_turn`**，别折成 N×5 tick |
| 3 | **读档能力** | `stackThreshold` + `thresholdTrigger`（到档触发什么）、`statPerStack`（每层载荷）、`ramp`、`phases`（形态轮转，如月相）——状态的 payoff 接口；「身份锚定」+7 分看这组是否非空 |
| 4 | **行为载荷** | `triggers`（15 封闭触发点 → effects，状态的主动面；挂载载荷用 `on_apply`）/ `modifiers`（自由词表修饰符）/ `behaviorModifiers` / `disallowActions` / 防御语义件（`lethalProtect` / `reviveBlocked` / `immune` / `suppress` / `redirectRule`…） |
| 5 | **跨系开关** | `crossPathway` + `participants` 白名单——不写默认途径私有；跨系联动评分维查这里 |
| 6 | **特殊机制件**（按需） | `formGroup` / `cycleTicks`（月相轮转）、`slots`（放牧槽 / 规则槽）、`lineageStack`（异类谱系）、`summonMapping`（刻印链）、`contagious`、`transferOnDeath` 等——用到才取 |
| 7 | **登记 + 数值** | 新 id 过词典对账、枚举过 check_enum_sync；数值处理同技能 |

> 状态层风格核对（2026-10-02 状态层矩阵批追加）：步 1 类别、步 4 触发点/状态面原语/修饰键三选一以上，
> 须对照 `途径设计身份.md §三·五` 的归属表——正主维度成体系（≥2 状态）、共享维度语义分叉、
> 禁入维度违反即打回；新修饰键先登记 glossary modifierKey 栏目再落卡面（登记制）。

## 被动设计审核：触发点与资源所有权（2026-10-17 立）

战意重构排查出的乌龙作为硬审核项；新被动卡必须逐条回答，答不上即打回：

1. **触发点与条件同尺度**：`on_battle_start` 只能读开局状态；死亡数、战况、资源层数等后续状态不得写在 battle_start 的 effect 里。要看后续战况，改用 `on_turn_start`（自身回合）或对应事件触发器。
2. **被动默认只读/生产，不消费共享资源**：被动自动消费会抢主动资源。确需消费必须显式设计、单独评审，并说明为什么不让主动技能消费。
3. **共享机制先定所有权**：同名机制在多张卡出现时，先回答“谁产生、谁持有、谁消费、叠不叠、上限多少、每回合限多少”，再写卡面。
4. **一次性/重复/复活再死写清**：触发是每次、每首次、每回合一次还是整场一次；复活是否回退、再死是否再计。禁止留“看实现”的模糊语义。
5. **条件主体写清**：host / caster / target / 事件源 / 全局；global 触发器还要写明事件源是谁（施法者 / 死者 / 被击杀者）。
6. **多被动同点竞争要验证**：同一触发点装 2–4 张被动时，顺序、叠层、资源竞争是否仍符合设计；同效果复制必须被机制去重或明确叠层上限。
7. **效果必须与触发语境匹配**：攻击结算类效果（如 reveal/识破）不能挂在 `on_battle_start` / `on_kill` 等无选靶语境上；被动只做持续修正或目标明确的事件驱动，效果写在哪就须能在那执行。
8. **身份状态单一主责**：一个身份状态只由一张卡承担主授予职责；其他被动不得挂载同名状态复制其主效果，要联动只能做读层 / 产层。禁止为了补齐评分维度再加一张重复身份卡——评分是诊断工具，不是设计目标。
9. **装备是卡，不是状态**：装备只能由 `kind:"equipment"` 的卡定义；打出即装备，被动卡不得直接装备。武器/护具两槽互相独立，同槽单实例，打出新件先下线同槽旧件。
10. **耐久在武器实例上**：`equipment.durability`（weapon 槽）为正整数、按普攻次数消耗、归零下线；护具槽走护甲池（`equipment.armor` = 池容量，池空下线、卸下清零）；不得用状态 `charges` / `duration` 表达装备寿命。
11. **开局装备用 initialEquip**：仅 passive 卡的 `initialEquip` 可在 `on_battle_start` 自动装备同途径装备卡；其他被动不得换装。装备不可驱散，卸下走 `disarm` / `recover_equipment`（下线并触发同槽公用 CD）。

## 召唤类技能审核（2026-10-20 立）

召唤卡的差异必须主要落在召唤物自身，而不是卡面通用效果：

1. **召唤卡引用的单位必须有显式 `unitDef`**，并由它承担主载荷：unitType / element / tags / reach / hp·atk 档位 / 攻击或亡语触发器。只存在于 DDD 归属表、JSON 无 Def 的单位视为未落地。
2. **卡面只负责**「召几只、落哪、何时、付什么代价」；通用施法者效果（modify_stat / mount_status / damage / heal / dispel）至多一段。
3. **`playable_scan.py` 的 `summon_unit_share` ≥ 50%** 为设计目标；低于 50% 的召唤卡在下一轮重设计时优先把效果迁入 unitDef。`missing_units` 非空 = 该卡引用的单位还没有 unitDef，先补定义再看占比。
4. `unitDef.triggers` 已接入引擎（spawn 时装配为召唤物被动），describe 仍须把蓝本攻击/亡语效果写清（玩家只读卡面）。

## 机制期玩法轨审核（2026-10-19 立）

> 与上面的「设计步骤」互补：这里问**玩家侧是否成立**，不是数据结构是否成立。
> 元规则三问（可感知性 / 成对检查 / 结果不挂手段）见 `WORKFLOW.md`。

### 逐卡 11 问（设计稿第 4 列）

1. 落哪个途径、哪个轴、产层还是读层？
2. **可操作性**：本卡的条件变量，本途径有 ≥2 张不同的卡能主动写入吗？（「有战意就能更强」不算）
3. 效果 AST 的原语/参数是否走闭环（选靶 → 条件 → 效果）？
4. **时机档位**：这张卡在哪个触发点/回合阶段起作用？换成别的时机会不会更好？
5. **代价**：不做这个选择会失去什么？代价必须与主收益**互斥**，且玩家能感知。
6. 硬约束自检（随机治理 / 位移 / 数值锚点）。
7. 文本三件套（describe 逐卡写，不得复用模板句）。
8. 附属定义块（状态/区域/界域）成对完整？
9. 元数据（conversionNotes / frameworkFlags / tentative / art）。
10. 元规则 2 四问：谁写、谁读、谁清（几条路径）、每条路径触发什么。
11. 过门禁（四脚本 + lint；机器门禁 10–13 见下）。

### 逐途径 7 问

1. 这条途径每个轴的代表玩法/机制是什么（轴锚点 `{kind, id}`）？一句话说清。**不得默认用状态+产层/读层套一切轴**；状态只是可选载体。
2. 可操作变量 ≥1（≥2 张卡主动写、≥1 张读、有代价）？
3. 集火时刻（真标记 + ≥3 张卡做**不同类型**反应 + 标记稀缺）？两条是不同轴，**不得合并成「有没有战术」**。
4. 四张手牌有几种出牌顺序明显更优？
5. 序列 9→0 的手法变了吗（不是「数值变大了」）？
6. 哪张牌改变这局打法？（`sampleBuilds` 中 ≥3/4 套出现的卡 = 无构筑分歧点）
7. 对手回合响应面：玩家在对手回合有可做的事/可预判的事吗？

### 机器门禁 10–13（`validate.py`，当前 warn，稳定后转 error）

| # | 条款 | 通过线 |
|---|---|---|
| 10 | 同形状增益叠加 | 单卡同键（stat/resource/status+mode）≤2 次 |
| 11 | 触发语境错配 | 无受害方事件（on_battle_start/on_kill/on_death）不得用受害方原语打 target；0 处 |
| 12 | 模板句复制 | 同途径效果节点 note 完全相同 ≤2 次（≥5 标「疑似批量注入」） |
| 13 | 被动触发点集中度 | 同一事件被动卡 <8 张 |

### 乘区纪律（2026-10-19 主人拍板）

- **同类取最优**：同单位的常驻 `damage_mul` / `damage_taken_mul` 取最优（输出取最大、承伤取最小），不叠乘、不求和。
- **优先加减法**：强度用护甲 / 护盾 / 攻击 / 防御等加值表达；乘区只作兜底。
- **一次性才用 `modify_damage`**：且不得无 duration 挂成常驻（当前内核将其记为永久修正，需逐卡注意）。
- **行动机会成本**：`opportunity: 0` 的技能/状态授予必须同时有 energy / cooldown 等资源约束，且不得形成无消耗循环（内核每次机会最多 2 次免费 Action）。

## 状态归属判定：公有 / 私有 / 分叉（2026-09-29 拍板）

新状态（或给既有 common 状态加玩法时）先按序过五条判据定归属：

| # | 判据 | 归属判定 |
|---|---|---|
| R1 | 有轴拿它当身份锚点（`axes.statusId` 指向）？ | → **必须私有**（落身份轴所在途径的 statuses.json）；common 不托管任何身份 |
| R2 | 身份状态被他途径 combo 消费？ | → 仍归本途径私有，标 `crossPathway:true` + `participants` 白名单（枢纽模式）；共享不转移所有权 |
| R3 | 概念通用但某途径要给它加层数经济 / 阈值玩法 / 主题化？ | → **分叉**：途径建私有变体（如 `intrigue_taunt`），common 原版原封不动留给通用引用 |
| R4 | 多途径日常使用、无人当身份、无层数经济？ | → **留 common**，不私有化 |
| R5 | 纯机制词汇（眩晕 / 沉默 / 护盾 / 减速 / 虚弱等）？ | → 无条件 common，永远不动 |

要点：

- **三档而非两档**：common（无主机制词汇）/ 途径私有（身份，含枢纽共享）/ 分叉（同名双版本）。
- 分叉时「身份用法 vs 通用用法」的逐卡区分口径：**读层（改层 / 条件读档 / 阈值）或当身份锚定的卡改指私有版；纯挂载当工具用的卡留 common 原版**。
- 评分侧背景：身份锚定 / 产层 / 读层三维只认途径自有状态，common 上的不算途径资产——这是私有化运动的动机，也是 R1 存在的理由。

## 技能与状态的接口契约

技能定义「一次性行为」，状态定义「持续语义」：卡面用 `mount_status` 产它、用
`modify_status` / 条件谓词读它。轴评分三维正是这个接口的契约检查
（2.14 起改兑现口径：声明面取自玩法蓝图，实证判据不变；旧三维退役为 legacyDims 诊断）：

- **锚点兑现 ↔ statusId/anchor**：蓝图声明的锚点 kind:id 与 axes 实录一致（旧「身份锚定」的层数引擎判据留档诊断，仍是好设计基线）
- **产层兑现 ↔ enabler 挂载实证**：蓝图产层段声明卡位是否真的挂了该身份（AST 可验）
- **收束兑现 ↔ payoff 读层引用**：蓝图消费段声明卡位是否有读层引用（landed），还是只在 notes 里自称（notes 级）

环节⑤重设计一张卡时，第 1–2 步（定位/骨架）基本不动，主要动第 3–4 步
（AST 与状态载荷）——即评分页失分项「修改意见」指向的那些。
