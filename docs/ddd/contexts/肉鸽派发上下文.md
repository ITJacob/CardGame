# 肉鸽派发上下文（Progression）

## 一、职责定位

肉鸽派发上下文负责**局外构筑与局内抽取**：这一局给玩家什么技能候选、抽到的技能怎么填进单位的槽位、重复抽到怎么办、技能怎么随升级阶梯变强。它处理的是"战斗开始之前"的所有不确定性，与"战斗开始之后"的确定性结算严格隔离。

它**不内联进战斗核心的 `SkillDef`**。战斗引擎只消费派发与构筑的最终产物——每个单位选定的 **4 主动 + 4 被动**蓝图。这条边界是为了不破坏"整场战斗一个聚合，根是 `Combat`"的固化原则。

```
progression 聚合                combat 聚合
┌─────────────────────┐      ┌─────────────────────┐
│ 抽池 / 候选 / 槽位   │      │ 根 Combat            │
│ 升级阶梯 / 重复规则  │ ───▶ │ 消费 4 主动+4 被动   │
│ 构筑校验             │ 快照 │ 蓝本，之后纯函数推进 │
└─────────────────────┘      └─────────────────────┘
       局外                          局内
```

## 二、核心实体

派发层沿 Definition + Grant 模式展开，但与战斗运行时完全解耦：

| 角色 | 内容 | 说明 |
|---|---|---|
| SkillDef（Candidate · 候选定义） | id、behaviorTemplate 引用、**派发元信息**（rarity / weight / pool / pathway / buildAxis / sharedAcross / desc / modes） | 挂在 Catalog 侧的可候选技能；战斗期只读，不参与结算 |
| BuildAxis（构筑轴） | axisId、pathwayId、keyword、playstyle | 途径内把技能池按玩法维度分组的方向轴 |
| BuildSlot（构筑槽位） | unitId、slotKind（active / passive）、index、filledSkillDefId | 单位最终的 4 主动 + 4 被动占位 |
| BuildSnapshot（构筑快照） | 每单位 BuildSlot[]、派生规则结果 | 战斗启动时原子灌入 Combat，之后 progression 与进行中的战斗无关 |
| UpgradeTrack（升级阶梯） | skillDefId、tiers[]（每档参数增量 / 形态选择） | 配合 `duplicatePolicy: upgrade` 分支 |

## 三、派发元信息（候选定义）

这些字段决定"这个技能在抽池里怎么被选中"，全部在派发层消费，不进战斗结算：

| 字段 | 取值 / 类型 | 职责 |
|---|---|---|
| `rarity` | 稀有度分级 | 决定抽取权重档位与展示，由途径序列位阶映射而来 |
| `weight` | number | 同一池内的相对抽取权重 |
| `pool` | poolId | 技能所属抽取池（按 run / 章节切换） |
| `pathway` | pathwayId | 途径维度，用于职业过滤 |
| `buildAxis` | axisId | 技能在所属途径构筑轴上的归属 |
| `sharedAcross` | pathwayId[] | 允许在同类型职业中重复出现的跨途径共享列表 |
| `desc` | string | 玩家视角文案，派发展示用 |
| `modes` | modeId[]（数据层） | 多选一 / 变体档，与升级阶梯同族实现，不进引擎 |

### 3.1 构筑轴（BuildAxis）

每条途径定义 **4 条构筑轴**，把该途径的技能池按玩法维度分组，使派发与构筑有可辨识的方向。4 条轴须覆盖本途径全部序列的能力谱系。

- 技能池内每个技能归属且仅归属一条构筑轴；每轴设一个旗舰技能作为该方向的强度锚点。
- 构筑轴只影响派发展示、分组与构筑引导，**不进入战斗结算**；引擎不感知 axisId。
- 跨途径共享沿**相邻途径**生效：同一源质分组内、序列位阶相邻的途径可重复抽到同一技能。

## 四、槽位约束（UnitDef）

单位持有固定槽位，派发时校验，不进战斗结算：

| 字段 | 默认值 | 说明 |
|---|---|---|
| `activeSlots` | 4 | 主动技能槽位数 |
| `passiveSlots` | 4 | 被动技能槽位数 |

战斗只接收填满后的蓝图；槽位本身不参与战斗内任何规则。

## 五、重复获得规则（duplicatePolicy）

肉鸽里重复抽到同一技能是常态，必须有明确规则：

| 取值 | 语义 |
|---|---|
| `upgrade` | 重复抽到 → 走 UpgradeTrack 升一档（参数增量 / 形态切换） |
| `reject` | 重复抽到 → 丢弃，重新抽或补发 |
| `stack` | 重复抽到 → 叠加实例（多层 Grant） |

## 六、与战斗聚合的边界

- **progression 是独立聚合**：抽池、构筑、升级全部在战斗启动前完成，结果通过 BuildSnapshot 一次性灌入 Combat。
- **战斗启动后只读**：Combat 只持有 BuildSnapshot 的副本，progression 侧的后续变更（即便存在）不影响进行中的战斗——与"战斗 ↔ Catalog 启动时快照"是同一铁律的局外版本。
- **引擎零感知**：战斗引擎不知道 rarity / weight / pool / duplicatePolicy 的存在，它只看到最终选定的 4 主动 + 4 被动蓝图。任何把派发概念泄漏进引擎的写法都违背本上下文边界。

## 七、不变量

- **INV-P1（边界）**：派发与构筑逻辑不得修改 `SkillDef` 的战斗期字段（behaviorTemplate 等），只能携带 / 选择派发元信息。
- **INV-P2（槽位饱和）**：灌入 Combat 的 BuildSnapshot 中，每单位 activeSlots / passiveSlots 必须填满且不超过上限。
- **INV-P3（共享约束）**：`sharedAcross` 标记的状态在跨途径复用时不改变其战斗期定义，仅扩展候选可见范围。
