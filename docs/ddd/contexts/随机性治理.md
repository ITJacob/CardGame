# 随机性治理（Randomness Governance）

## 一、为什么这是硬需求

战斗结果必须是确定的、可复现的。项目已有 20 万局蒙特卡洛验证与回放系统——散落的 `Math.random()` 会让回放不可复现、验证不可回归：今天 50:50，明天 49.8:50.2，你将无法判断差异来自改动还是噪声。因此随机性不是洁癖，而是验证与回放基础设施的前提。

完整的确定性闭环由两部分构成：Catalog 快照（INV-C3，战斗启动时固定外部配置）＋ 随机源治理（本篇，战斗启动时固定内部随机）。二者合起来才保证：结果 = f(初始状态, 输入序列, 种子)，同三者相同则结果逐位相同。

## 二、治理规则

| 规则 | 内容 |
|---|---|
| R1 | 默认零随机：伤害链、治疗、资源增减、目标选择，默认路径上不存在任何抽样 |
| R2 | 概率必须走 RandomSource：显式、可注入、可播种；种子在战斗创建时确定并写入战斗记录 |
| R3 | 登记制：引入概率的效果必须被显式标记，可被平衡审计工具筛出单列，逐个评审 |
| R4 | 单次抽样：随机源只在生效条件判定处被读取一次，禁止在结算链内部二次抽样 |
| R5 | 建议边界：概率用于非伤害维度（是否挂载附加状态、触发哪条附加效果）；伤害/治疗数值保持确定；目标选择不引入随机 |
| R6 | 可复现契约：战斗结果 = f(初始状态, 输入序列, seed)。同三者相同，结果必须逐位相同 |

## 三、与效果类型的配合

`EffectCondition` 中的 `Chance` 是唯一允许引入随机的条件，且必须经由 RandomSource。任何效果若引入概率，必须在配置中被标记（R3），以便平衡审计工具筛出评审。在建议边界（R5）下，概率应限于"是否附加状态"这类非伤害维度——例如某火系技能"50% 概率挂灼烧"可以保留，但必须走 RandomSource 并登记为随机效果。
