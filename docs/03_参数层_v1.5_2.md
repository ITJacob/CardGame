## 3. 数值冲突与裁定

### 3.1 ✅ 已裁定 · B3 · laneRef: auto 破坏流水线纯函数性

问题：auto 需要读取施法单位自身的射程属性才能解析，使 calculateTargets 依赖施法者上下文，不再是纯函数。
建议：在 I 节点之前增设"施法者上下文预处理"步骤，把 auto 解析为具体值（same_lane 或 all_lanes），再进入流水线。
代价：多一步；收益：流水线保持纯函数，可独立测试与缓存。

✅ 裁定结果（2026-08-29）：在 I 节点之前预处理。实现时对应主文档 §14.2 第 6 项——需从配置里找出所有 laneRef: auto 并验证解析结果。

### 3.2 ✅ 已裁定 · scope: radius 删除，改用 adjacent + spread

问题：whirlwind 用了 scope: radius，但取值域定义里只有 single_point / whole_lane / adjacent，radius 未在目标系统定义。
裁定建议：要么在目标系统补充 radius 的语义（以锚点为中心、跨路的半径范围），要么把 whirlwind 改用 adjacent + spread 组合表达。建议后者——避免新增一个与其他 scope 语义重叠的维度。

✅ 裁定结果（2026-08-29）：采用后者。从取值域删除 radius，旋风斩改用 adjacent + spread 组合。§1.1 已同步更新。

### 3.3 ✅ 已裁定 · 中毒：时长与伤害口径冲突

✅ 裁定结果（2026-08-29）：采 v1.3。StatusDef.defaultDuration = 5，与 StatusGrant.duration = 5 一致（§2.4 已回填）。

### 3.8 ✅ 已裁定 · B7 · 近战对撞是否校验"目标够得着攻击者"

问题：近战对撞发生时，被打的目标是否必须"够得着"攻击者才还击？
场景：刺客越位攻击敌方排尾单位——排尾单位自己的攻击行为是否够得着刺客？

|||
|---|---|---|
|不校验（我的建议）|近战一律对撞，规则简单、玩家可预期|越位刺客会稳定吃到对撞，可能削弱越位收益|
|校验可达性|更符合"贴身互搏"直觉|需为每个攻击行为再算一次反向可达性，实现与心智成本都高|


建议首批不校验，作为扩展点保留；等实测发现"越位刺客无脑白嫖"再补。

✅ 裁定结果（2026-08-29）：首批不校验可达性，近战一律对撞。可达性校验作为扩展点保留。

### 3.9 ✅ 已裁定 · B8 · 术语多段伤害：一个 Action 还是多个 Action

问题：「风怒 = 连续造成两次伤害」在运行期是一个 Action 内的两段效果，还是两个独立的 Action？

|||
|---|---|---|
|同 Action 内多段（我的建议）|一次交手掉两截血；只触发一次对撞 / 一次受击 / 一次反击|第一段打死后第二段打空|
|每段一个 Action|真的是"两次攻击"，近战对撞 N 次|与玩家心智不符；事件量与结算次数翻倍；目标可能被重选|


连带需要一起定的：目标死亡后第二段是打空还是溢出重选（我建议打空，符合"单位只是坐标的临时租客"）。

✅ 裁定结果（2026-08-29）：同 Action 内多段。只撞一次、只触发一次受击/反击；第一段打死后第二段打空，不重选。

### 3.10 ✅ 已裁定 · 抗性口径：线性减法 vs 百分比乘区

问题：抗性 30 是"减 30 点伤害"还是"减 30% 伤害"？

|||
|---|---|---|
|线性减法|与防御同口径，实现简单|高抗性下小额伤害被吃到 0；数值难以跨血量/伤害量级复用|
|百分比乘区（我的建议）|比例直观，跨量级稳定|需明确与"易伤/坚守"乘区是加算还是连乘|


建议：走乘区，且与易伤/坚守在同一乘区内先加算、再统一乘一次，避免乘区数量爆炸；并强制上下限钳制。


这条不定，§2.6 的防御杠杆就无法完成重新标定——它和 §3.5 是同一件事的两面。

✅ 裁定结果（2026-08-29）：走百分比乘区，与易伤/坚守在同一乘区内先加算、再统一乘一次，并强制上下限钳制。至此伤害侧口径全部统一为乘区。

### 3.11 ✅ 已裁定 · B9 · 元素与伤害大类是否拆两层

问题：你给的六个取值里，"物理""精神"更像伤害大类，其余是元素标签。要不要拆成 element × damageCategory 两层？

|||
|---|---|---|
|只用一层（当前默认）|六元素各有一槽抗性，物理抗性就是"护甲"|将来要做"护甲只减物理 / 抗性只减魔法"时需返工|
|拆两层|结算走 damageCategory，元素只作标签|抗性槽位与 UI 复杂度上升|


我已按"兼容两层"建模：结算只走 element（逐元素取抗性），damageCategory 作为只读派生先备着，不拆也能正常用。此项不阻塞，等你真需要时再启用。

✅ 裁定结果（2026-08-29）：不拆两层，只走 element 一层（六元素六抗性槽，物理抗性即护甲）。damageCategory 保留为只读派生（INV-EL3），将来启用零成本。
