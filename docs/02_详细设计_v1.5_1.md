# 卡牌对战系统 · 领域模型详细设计 v1.5




本文是《领域模型抽象 v0.2》的落地展开。v0.2 只给概念清单与待拍板项，本文给字段级契约、生命周期状态机、不变量的形式化表达、聚合边界与一致性范围、核心流程序列。
本文仍不含具体数值与平衡参数——那些归《参数层》，作为独立文件在骨架定稿后回填。
涉及枚举时只给维度名与语义，具体取值域见参数层。

v1.1 增补
1. 攻击类型（reach）：近战 / 远程是攻击类行为的属性，与站位解耦。新增近战同步对撞结算规则；扩展 RedirectRule 支持守卫姿态（按坐标关系拦截特定来源伤害）；新增 stance 状态分类与「硬控清除姿态」规则。见 §5.9、§7.5。
2. 目标选择模式（selectionMode）：自动选目标 vs 玩家手动选目标；I 节点拆为「候选池 → 收缩」两段；Manual 模式必须带确定性兜底。见 §7.3、§10.1。

v1.2 增补
3. 元素属性（Element）：火 / 冰 / 毒 / 电 / 精神 / 物理。元素是纯标签，自身不带数值语义，一切意义由抗性、状态触发、流派规约等外部机制赋予；挂在 effect 层而非 behavior 层；DamageChain 新增「抗性型」阶段。见 §8.3。
4. 术语（Term）：一组有名字的固定行为内容参数，给人理解（Effect 给系统理解）。用于技能设定、流派制定、玩家理解。在编目期展开为扁平 EffectRef 序列，运行期引擎零感知，仅留 originTerm 溯源烙印。见 §8.4。

v1.3 增补：12 项待拍板事项全部裁定完毕（B3 / B7 / B8 / B9 / §3.2–§3.7 / §3.10 / A2′），结论见 §0 决策记录 A12–A16 与参数层 §3。
数值口径定调：伤害乘区化——易伤走 ×1.3 乘区、抗性走百分比乘区，二者在同一乘区内先加算、再统一乘一次。连锁后果：原「防御 ±1 = ∓50% 普攻输出」杠杆失效，需重新标定。

v1.4 增补：进入技能设计阶段，新增 A17–A20——术语算子集扩为 Sequence / Repeat / If（跨效果传值做成独立 EffectDef）；抗性钳制 [-50%, +75%]、档位 10%；SkillDef 采模板优先 + 逃生舱；推进顺序为先术语词汇表、再设计技能。

v1.5 增补：效果类型族审计。类型 7 → 9（补 dispel、登记 drain）；划清 heal / modify_resource（A22）与 modify_stat / mount_status（A21）；区域载荷清单化 + 陷阱定位（A23）。
并修复一个 bug：带 duration 的 modify_stat 原先无人计时、永不回滚——改由 StatProvenance 条目自带 remaining，tick 第 6 步递减（§6.1）。
顺带修正一处长期错误的计数：此前各版称"不变量 40 条"，实为 43 条（v1.4）；本次新增 4 条（INV-D5 / INV-P7 / INV-B8 / INV-S5）→ 47 条。§12 已改为在表头声明总数，避免再次漂移。

## 1. 一个必须先定的架构判断：聚合边界

在细化过程中，我遇到一个绕不开的问题：Unit 到底是不是聚合根？

标准 DDD 建议聚合尽量小，Unit 看起来天然是聚合根。但本系统的核心不变量——坍缩后队列无空洞、同一时刻只有一个单位在行动、转向后目标仍是合法坐标——全都横跨多个单位。若 Unit 各自成聚合，这些不变量没有任何聚合内能保证。

判断：上下文是逻辑边界，聚合是事务边界，二者不必重合。


整个战斗是一个聚合。根是 Combat（战斗），Unit 是聚合内的实体。

|||
|---|---|
|不变量横跨单位|队列坍缩、先手序列、转向防环，都是跨单位规则|
|规模有限|双队 × 双路 × 每路固定格数，上限在十几个单位量级，聚合过大不是风险|
|内存模型|战斗是全内存、单线程、确定性推进的，不存在并发争用|
|一致性要求|一次结算要么全生效要么不生效，部分成功会产生不可解释的战局|


代价与缓解：聚合变大后，内部用"上下文"做逻辑分层（战场 / 编队 / 调度 / 执行 / 效果），各层只通过明确接口访问，不允许跨层直接改字段。这样既保住了事务安全，又不至于变成一坨。

Catalog 是独立聚合：定义态数据不可变、无事务需求、可全局缓存与共享，与战斗运行时完全解耦。

## 2. 通用模式：Definition + Grant

### 2.1 命名表（A3）

||||
|---|---|---|
|EffectDef|—|EffectRef（引用实例）|
|BehaviorTemplate|SkillDef|BehaviorSlot|
|StatusDef|StatusGrant|StatusInstance|
|ZoneDef|ZoneGrant|Zone|
|ClassDef|—|（解析后消失）|
|TermDef|TermGrant|（编目期展开后消失，只留 originTerm 烙印）|


元素不属于本模式：Element 是枚举型标签值对象，没有"默认 / 覆写 / 实例"三层，直接挂在 EffectDef 上（§8.3）。

### 2.2 统一契约

实例化(Def, Grant):
    value = Def.默认值
    value = Grant.指定值 ?? value        // 覆写
    value = clamp(value, Def.下限, Def.上限)   // 钳制
    return Instance

三条铁律
1. 默认值与上下限只写在 Def，实例值只写在 Grant。任何一处都不许两写。
2. Grant 是值对象，创建后不可变；Instance 持有它的副本。
3. Def 不可变、可缓存、可共享；同一 Def 可产生任意多个不同 Grant 的实例。

### 3.1 一致性边界

|||
|---|---|
|一次「结算步骤」内的全部变更|强一致（原子）|结算步骤 = 一个 Action 从点火到落地的完整过程；失败则整体回滚到步骤开始前的战斗快照|
|一个 tick 内的全部推进|强一致|资源累积、引导/冷却递减、引导完成结算，作为一个原子步|
|战斗 ↔ 战斗|无一致性需求|各战斗独立|
|战斗 ↔ Catalog|启动时快照|战斗创建时把所引用的全部 Def 快照进战斗内，之后配置变更不影响进行中的战斗（保证回放与验证可复现）|
|战斗 → 外部（UI / 回放 / 统计）|最终一致|通过领域事件异步广播，不参与战斗一致性|


快照 Catalog 这条与 B1 的确定性铁律是同一件事的两面：外部输入（配置）与内部随机（RandomSource）都必须在战斗启动时被固定，战斗才是一个纯函数——结果 = f(初始状态, 输入序列, 种子)。

## 4. 战场上下文（详细）

### 4.1 概念模型

||||
|---|---|---|---|
|Coordinate|值对象|faction, lane, index|全局唯一、结构稳定；不随任何单位迁移而改变；可比较、可作字典键|
|Slot|值对象|occupant: UnitId \| null|一个可占位单元；空用 null 表示|
|Lane|实体|id, slots: Slot[]（定长）|一条线性队列；index 从对峙线向队尾递增|
|Faction|实体|id, lanes: Map<laneId, Lane>|战场的一方|
|Battle|实体（战斗聚合内）|factions, zones: Zone[]|空间容器；持有全部坐标空间与区域挂载物|
|ZoneDef|实体（Catalog）|id, kind, 默认 ZoneGrant 模板, 生命周期上限|区域类型本体|
|ZoneGrant|值对象|duration, uses, affects, trigger, triggerOnExisting, effects: EffectRef[], ownerSide, sourceId|本次放置的参数包；载荷是清单（A23），逐条独立判定|
|Zone|实体|id, coord, grant: ZoneGrant|绑定坐标的持续效果；以坐标为唯一键|


### 4.2 不变量（形式化）

设 L 为一条 Lane，occupied(L) = { i | L.slots[i].occupant ≠ null }。

|||
|---|---|---|
|INV-B1|容量|\|occupied(L)\| ≤ \|L.slots\||
|INV-B2|无内部空洞|occupied(L) = {0,1,…,k-1}（必须是前缀）|
|INV-B3|即时紧凑|任何占位变更后，collapse 必须在同一原子步内完成|
|INV-B4|坐标唯一|∀u ∈ Units, coordOf(u) = (f,l,i) ⟺ Battle[f][l].slots[i].occupant = u.id|
|INV-B5|投影只读|Unit.position 只能由 Placement 写入；其他任何模块读多写零|
|INV-B6|区域解耦|Zone.coord 与 Zone 生命周期均不依赖任何 UnitId|
|INV-B7|满则拒绝|isFull(L) → insert 被拒绝（不静默丢弃，返回失败原因）|


### 4.3 Placement：唯一占位出口（A1 落地）

契约：所有改变占位的操作必须且只能通过 Placement。它是战场上唯一有权写 Slot.occupant 与 Unit.position 的组件。

|||
|---|---|---|
|insert(unit, coord)|目标 lane 未满；coord 合法|写入 slot → collapse → 刷新投影 → 发 OccupancyChanged|
|remove(unitId)|单位在场上|置空 slot → collapse → 刷新投影 → 发 OccupancyChanged|
|swap(a, b)|两者均在场|交换 slot → collapse → 刷新投影 → 发 OccupancyChanged|
|relocate(unit, coord)|目标 lane 未满|原位置空 → 新位置写 → 双端 collapse → 刷新投影 → 发事件|
|applyExternal(mutator)|—|快照 → 执行 mutator → collapse → 校验门禁 → 通过则提交，否则回滚到快照|


执行模板（每个操作统一走这个流程）：

1. snapshot ← 当前 Battle 空间结构
2. next ← 执行变更
3. next ← collapse(next)                    // INV-B3
4. next ← syncProjections(next)             // INV-B4 / INV-B5
5. if !invariantCheck(next) then return snapshot, Failure(reason)   // INV-B1/B2/B7
6. occupancyDiff ← diff(snapshot, next)     // 进入/离开某坐标的单位集合
7. emit(OccupancyChanged(occupancyDiff))    // 供 Zone 订阅
8. return next, Success


第 7 步是 Zone 触发的唯一入口——Zone 不监听"移动"这个动作，只监听"占用关系变化"这个事实。这条让击退、召唤、死亡补位、跨路移动全部自动获得区域触发能力，无需逐个特判。

### 4.4 Collapse 契约

collapse(Lane) -> Lane'
  取出 slots 中所有非空 occupant，保持相对顺序，从 index 0 起依次填回，其余置 null
  副作用：刷新每个被移动单位的 position 投影

- 幂等：对已紧凑的 Lane 调用，结果与原值相等。
- 不改变相对顺序（队列语义）。

### 4.5 Zone 生命周期

   place(ZoneDef.id + ZoneGrant)
        │
        ▼
   ┌─────────┐  triggerOnExisting=true   ┌──────────────┐
   │ Created │──────────────────────────►│ 结算在场单位  │
   └────┬────┘                           └──────────────┘
        │（默认 false：在场者不触发）
        ▼
   ┌─────────┐   OccupancyChanged(enter, coord 命中且阵营匹配)
   │ Active  │──────────────────────────► 逐条执行 ZoneGrant.effects（各带 condition）
   └────┬────┘                            消耗 uses（若定义了，整次触发算一次）
        │
        ├── duration 耗尽 ──► Expired
        ├── uses 耗尽 ─────► Expired
        └── 被显式移除 ────► Removed

关键语义（沿用你已拍板的决策）：进入判定用 before/after 两张战场快照做 diff——凡在 after 中处于某 Zone 坐标、且在 before 中不处于该坐标者，判定为进入。坍缩导致的落入视同进入，同坐标换人（A 死 B 补位）也判定为进入。
