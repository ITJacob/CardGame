## 8. 效果上下文（详细）

### 8.1 三件套

EffectDef（Catalog · 不可变）: id, type, 默认参数, 元标记（如 bypassArmor）
EffectRef（运行时引用实例）  : ref, params（覆写）, condition, target（覆盖）
Effect（执行体）             : 由 EffectDef + EffectRef.params 组合而成

效果类型族（只定义职责，数值归参数层）

|||||||||
|---|---|---|---|---|---|---|---|
|1|damage|造成伤害|效果 → DamageChain|✅|—|已定义|
|2|heal|治疗语义地恢复池型资源|编队|❌|—|已定义（A22 划界）|
|3|mount_status|挂载状态|编队（StatusDef + StatusGrant）|❌|间接（状态实例）|已定义|
|4|modify_stat|写入无宿主属性修正|编队（StatProvenance）|❌|✅|已定义（A21 划界）|
|5|modify_resource|直接增减池/进度资源|编队|❌|—|已定义（A22 划界）|
|6|move|位移|战场（必须经 Placement）|❌|—|已定义|
|7|spawn|生成单位|战场（Placement）+ 编队（建 Unit）|❌|—|已定义|
|8|dispel|驱散（清状态 / 拆区域）|编队（单位目标）· 战场（坐标目标）|❌|触发回滚|A23 新增|
|9|drain|吸血（先伤后回，效果内部闭环）|效果内部|✅|—|A17 裁定，本版登记|


heal vs modify_resource（A22）
- heal 是治疗语义：未来要吃"治疗加成 / 治疗减益"修正，只作用于池型资源中的生命类。
- modify_resource 是直接资源操作：绕过一切修正，用于支付、消耗、设定值（如"献祭 3 生命""回复 5 能量"）。
- 判别：这个数值应不应该被治疗修正影响？应该 → heal；不应该 → modify_resource。
modify_resource 的作用范围（A24）
| 组 | 键 | 语义 | 钳制下限 |
|:---|:---|:---|:---:|
| Pool | hp / energy / shield / armor（当前值） | 池型资源的当前值 | 依资源定义 |
| Gauge | gauge.current | 行动条当前进度（击退 = 扣它） | 0 |
| Gauge | gauge.rate | 每 tick 累积速率（加速 / 减速） | 0 |
| Gauge | gauge.threshold | 触发阈值 | 1 |

⛔ 行动周期 = threshold / rate 是派生值，禁止被 modify_stat 直接修正（INV-S5），只能改上面两个源属性。

modify_stat vs mount_status（A21）
二者在"属性修正 + 撤销"上同构（都走 StatProvenance），但宿主不同：前者无实例、不可驱散、无层数、无触发器；后者是 StatusInstance，能力全开。
判别规则：需要被玩家看见 / 可被驱散 / 可叠加 / 带触发器或行为约束 → mount_status；纯粹的、不可交互的面板修正 → modify_stat。
⚠️ 带 duration 的 modify_stat 不产生 StatusInstance，其计时由账本条目自带 remaining 负责（tick 第 6 步递减，见 §6.1），到期 revertBySource。

drain 为什么是独立类型而不是术语（A17）
它的后一段（回血）依赖前一段的实际结算结果（可能被护盾吃掉、被抗性削过），编目期无法确定入参。硬塞进术语会破坏"编目期展开成扁平 EffectRef"的根基（INV-T1）。由引擎在单个效果内部闭环：先算伤害 → 再按结果回血 → 只发一条 EffectApplied。

dispel 的目标与边界（A23）
| 目标 | 行为 |
|:---|:---|
| unit | 清除 StatusInstance（按 dispelable / category / count 过滤）；不碰属性修正（INV-P7） |
| coordinate | 移除该坐标上的 Zone（"拆陷阱"） |

### 8.2 DamageChain

建模为有序的减伤阶段管道，而不是硬编码的两步。

DamageChain {
    stages: MitigationStage[]     // 顺序固定，配置决定组成
}

resolve(raw, attacker, defender, chain):
    cur ← raw
    for stage in chain.stages:
        cur ← stage.apply(cur, attacker, defender)
    return DamageResult { raw, stageBreakdown, final }

阶段类型

|||
|---|---|---|
|吸收型|优先扣减一个消耗性资源池，扣完为止|护盾 / 护甲|
|减免型|线性加减（可为负 → 增伤）|防御|
|抗性型|按防守方对本次伤害元素的抗性做修正，逐元素取槽|火抗 / 冰抗 / 毒抗 / 电抗 / 精神抗 / 物抗|
|乘区型|乘性修正|易伤 / 坚守|
|穿透标记|跳过后续若干阶段|DoT 穿透护甲|
|下限钳制|最终结果的下限|最低伤害保底|


抗性型插在减免型之后、乘区型之前，与"防御线性减伤"是两笔独立的账，不合并成一个数。抗性阶段自带上下限钳制（避免 100% 免伤与负抗性无限放大）。

不变量
- INV-D1：阶段顺序固定且配置可见，不允许在代码里散落修改。
- INV-D2：结算全程无随机（B1 铁律）；DamageResult 必须可由输入完全复现。
- INV-D3：伤害链是纯函数——不改任何状态，只产出 DamageResult；状态变更由 O 节点依据结果执行。
- INV-D4：状态来源的伤害不进通用乘区（原 §7.3 已拍板）；如需进入，必须在 EffectDef 上显式开关，不默认进入。
- INV-D5：heal 与 modify_resource 不得混用——同一次资源增加只能走其中一条路径（A22）。


INV-D3 很重要：把"算"和"改"分开，才有了 R 节点预计算 settlementPlan、O 节点只做应用的可能（B2 的解决前提）。

### 8.3 元素属性（Element，v1.2 新增）

核心判断：元素是一个纯标签，自身不带任何数值语义。

这句话是本节的地基。元素的"意义"全部由外部机制赋予：抗性属性、状态触发条件、区域/地形互动、流派规约。引擎不认识"火"，引擎只认识"effect.element == X → 去查 X 对应的抗性槽"。

|||
|---|---|
|写进引擎（if element == fire then 灼烧）|加一个元素要改引擎；元素之间无法复用规则|
|只作标签（推荐）|加元素 = 加一行配置；"火伤附加灼烧"是数据而不是代码|


取值与两个层次

EffectDef.element  : fire | ice | poison | shock | mental | physical | none
DamageCategory     : physical | magic | true      ← 由 element 经「编目映射表」派生

六个取值里，"火冰毒电"是元素标签，而"物理""精神"更像伤害大类。混在一个枚举里短期没问题，但一旦要做"护甲只减物理 / 抗性只减魔法"就会返工。所以显式给出第二层：

- 结算按 element 逐项取抗性（六槽各算各的）。
- damageCategory 是只读派生，服务于 UI 分组、流派规约，以及"护甲只减物理"这类未来规则；默认不参与结算。
- 好处：你现在只想用一层，就只用一层；将来要两层也不用改模型，映射表是配置。


✅ B9 已拍板：不拆两层，只走 element 一层（六元素六抗性槽，物理抗性即护甲）。damageCategory 仍作为只读派生保留（INV-EL3），将来真需要时启用零成本。

挂在哪一层

元素挂在 EffectDef（可被 EffectRef.params 覆写），不挂在 BehaviorTemplate 上。

- 一次行动可以产出多段不同元素的伤害（"砍一刀物理 + 附加一跳火焰"）。
- 技能卡面上的"这是个火系技能"是派生：derivedElements = union(全部 effect 的 element)，只读、缓存、不双写。
毒的解耦（容易踩的坑）

element = poison 是伤害的属性标签，"中毒"是 StatusInstance。二者互不隐含：

- 毒元素伤害 不必然施加中毒状态；
- 中毒状态的跳伤 通常带 poison 元素，但那是由状态本体声明的，不是默认行为。
桥接一律走状态本体的触发表声明——是数据，不是代码：

StatusDef(burn).triggers += on: DamageDealt(where element == fire) → mount self

不变量

- INV-EL1：元素是纯标签，自身无数值语义；一切语义由外部机制（抗性 / 状态触发 / 流派规约）赋予。
- INV-EL2：元素挂在 effect 层，不在 behavior 层；一个 Action 可产出多段不同元素的伤害。
- INV-EL3：damageCategory 是 element 的只读派生，映射表单点定义于 Catalog。
- INV-EL4：元素与状态互不隐含——poison 元素不隐式挂中毒，中毒也不隐式改变伤害元素；桥接必须显式配置。
对既有机制的改动面（都很小，因为元素只是个标签）

|||
|---|---|
|§8.2 DamageChain|新增抗性型阶段（减免后、乘区前），自带钳制|
|§5.2 属性模型|新增 ResistanceSet，逐元素一槽，复用既有三层与溯源账本|
|§10.3 EffectCondition|新增 ElementIs(...) / ElementIn([...]) 谓词|
|§5.9 sourceFilter|可按需扩展元素维度（如"只挡火焰远程"）|


### 8.4 术语（Term，v1.2 新增）

定位：Effect 是给系统理解的；Term 是给人理解的。

|||
|---|---|---|
|面向对象|引擎|设计者 / 玩家|
|粒度|最小可执行原语（造成一次伤害）|一组有名字的固定参数组合|
|是否参与结算|是|否（展开后即消失）|
|会不会被撤销|是（走溯源账本）|否（不是运行态实体）|
|典型|damage { ratio: 1.0 }|风怒：连续对同一目标造成两次伤害|


术语回答的是"这一坨效果叫什么"，而不是"引擎该怎么算"。它同时服务于三件事：技能设定（写技能时直接引用"风怒"，不用手搓两条伤害）、流派制定（"风怒流"以术语为聚合条件）、玩家理解（卡面上显示的名字与描述）。

它不是什么

- 不是行为：术语没有 targetSpec、没有消耗、不占行动机会。它填充行为，不是替代行为。
- 不是状态：不挂在单位上、没有时长、不会被驱散。
- 不是标签：术语带内容（一组固定的行为参数），标签只是它的副产品。
结构

TermDef（Catalog · 不可变）
    termId       : "wind_fury"
    displayName  : "风怒"
    category     : attack_shape | rider | trigger | mobility | guard | ...
    description  : 玩家可读文本（模板，含占位符，由实参渲染）
    composition  : TermComposition
    overridable  : [count]            // 允许被覆写的参数白名单，默认空 = 完全固定
    tags         : [multi_hit, ...]   // 流派 / 检索用

TermComposition（首批**三个**算子，其余留作扩展）            // A17
    Sequence(of[])                          // 顺序执行
    Repeat(body, count, shareTarget)        // 重复 count 次；shareTarget=true 则共享同一冻结坐标
    If(cond, then[], else[]?)               // 条件分支；cond 直接复用 EffectCondition 谓词，零新增概念

风怒 的最小表达：

Term wind_fury:
    composition = Repeat(body = [EffectRef(damage, { ratio: 1.0 })], count = 2, shareTarget = true)

斩杀 的最小表达（If 的条件直接复用 §10.3 的谓词，不新造条件语言）：

Term execute:
    composition = Sequence([
        EffectRef(damage, { ratio: 1.0 }),
        If(cond = TargetHpBelow({ ratio: 0.3 }),
           then = [ EffectRef(mount_status, { status_id: burn }) ])
    ])


⚠️ 术语的边界：不做跨效果传值。
「吸血」这类「后一段的数值依赖前一段的实际结算结果」的效果，不能用术语表达——它需要引擎在效果之间传值，会破坏「编目期展开成扁平 EffectRef」的根基（INV-T1）。
正确做法：做成独立的 EffectDef(drain)，由引擎在单个效果内部闭环（先算伤害、再按结果回血、只发一条 EffectApplied）。术语只负责编排，不负责计算。
判别规则：一段效果的入参能否在编目期就确定？能 → 术语；必须等运行期结果 → 独立 EffectDef。

展开时机：编目期，不是运行期（A11）

这是本节最关键的判断。

BehaviorTemplate.effects : [EffectRef | TermRef]      // 有序列表，就地展开
    │
    │  Catalog 编译 —— 战斗启动前，一次性完成
    ▼
BehaviorTemplate.effects : [EffectRef]                // 扁平序列，每个带 originTerm 烙印

- 运行期引擎完全不知道"术语"的存在，只看到一串扁平 EffectRef。→ 确定性、回放、既有管线零改动。
- 展开时把 originTerm（完整引用路径，支持嵌套）烙印进每个产出的 EffectRef，只读、不参与任何结算。→ "这次伤害来自风怒"在战报、UI 高亮、流派统计里依然可查。


这是「编译期宏 + 溯源烙印」，和 A7 的 Definition+Grant、A6 的 StatProvenance 是同一个套路：定义期给语义，运行期只留痕迹。术语因此不会变成第二条执行路径——那才是架构真正的风险。

覆写：沿用 Definition + Grant

TermGrant { termRef: "wind_fury", overrides: { count: 3 } }

- 覆写项必须在本体 overridable 白名单内，否则编目期报错（INV-T3）。
- 展示文案由实际生效参数渲染，不允许与实参脱节——"风怒"真打三下就必须显示三下，或改名（INV-T4）。否则玩家会觉得被骗，这是体验事故，不是小瑕疵。
术语多段 = 一个 Action 内多段（B8 已拍板）

这个选择后果很大，摆清楚取舍：

|||
|---|---|---|
|近战对撞|只撞一次（对撞是交手级语义）|撞 N 次|
|目标解析|走一次 I 节点|走 N 次|
|受击 / 反击触发|触发一次|触发 N 次|
|玩家心智|"打了一下，掉两截血"|"打了两下"|


裁定：同 Action 内多段、共享冻结坐标（INV-T5）——你的原话就是"连续给对方（同一个）造成两次伤害"，且坐标在 I 阶段已经冻结了。

已接受的代价：第一段把目标打死，第二段打空（打到空坐标），不重选。这符合"单位只是坐标的临时租客"的既有哲学，也让玩家可预期。"溢出重选"作为可选开关保留，非默认。

嵌套与环路

允许术语引用术语（烈风怒 = Repeat(风怒, 2)），展开在编目期递归完成，引用图必须无环（INV-T2，加载时静态检查）。

流派 = 基于术语与元素的规约，不是新实体

复用 §10.3 的组合谓词即可，输入"卡组 / 技能集合"，输出"是否归属 + 契合度"；纯查询，不进战斗：

Archetype(风怒流) = count(HasTerm(wind_fury)) >= 2
Archetype(火法流) = ratio(EffectElement == fire) >= 阈值

不变量

- INV-T1：术语在编目期展开为扁平 EffectRef 序列；运行期 Action 只见 EffectRef，引擎零感知。
- INV-T2：术语引用图无环，Catalog 加载时校验。
- INV-T3：TermGrant.overrides 的键必须是 TermDef.overridable 的子集。
- INV-T4：术语展示文案由实际生效参数渲染，禁止与实参脱节。
- INV-T5：术语内多段默认共享同一冻结坐标，段间不重新解析目标；目标死亡则后续段落空。
