## G10 · 一次性反应型状态（consumeAfterTrigger）

> 由愚者·小丑戏法修改需求引出。用户要求"预置一个状态，在下次受到攻击时触发一次"。

### 问题
引擎 `StatusDef.triggers: TriggerDef[]` 的 `on_take_damage` 触发点**每次受击都会重复触发**（在 duration 内），`TriggerDef` 当前只有 `event / effects / sourceFilter / condition`，**没有"触发一次后消耗"的字段**。"下次受到攻击时触发一次"需要状态在触发后自动卸载。

### ✅ 结论更正（2026-08-31 复核）：**无需新增字段，C6 次数机制已实现**

复核引擎代码后发现本条立项时判断有误，实际**已具备能力**：

- `StatusDef.charges` / `StatusGrant.charges` 已存在（`src/catalog/model.ts:231` / `:247`）。
- `StatusInstance.chargesRemaining` 已存在（`src/roster/status.ts:31`），注释明确：「次数型状态（C6）剩余次数……由 `fireEventTriggers` 在每次响应式派发后递减，归零即卸载（`reason: 'consumed'`）」。
- `fireEventTriggers`（`src/combat/combat.ts:358` 起）已实现递减与统一卸载逻辑。

**所以「触发一次后消耗」直接写 `charges: 1` 即可**，不用新增 `consumeAfterTrigger`。`clown_dodge` 的 `charges: 1` + `defaultDuration: 2` 正是「2 tick 内首次受击触发一次，随后卸载」的正确表达。

> 保留本节作为结论记录，避免日后重复立项。

### 状态登记（愚者·小丑戏法专用，新增）
- `clown_dodge`：`category: buff`、`dispelable: true`、`maxStacks: 1`、`defaultDuration: 2`；触发器 `on_take_damage` → `move(push_back, distance: 99)`（己方半场退后排，复用 G8/C1 的 `push_back`，**不新增 move.op**）+ `mount_status(shield, +3, 3t)`。
- 该状态不进 F 组通用表（途径特有），复用已落地的 **C6** 次数机制（`charges: 1` 表达"触发一次后卸载"），随愚者核对闭环登记于此。

## G12 · 免疫负面状态（disguise / immune 字段）

> 由愚者·易容修改需求引出。用户要求"易容改为一段时间内免疫负面buff"，而非事后清除。

### 问题
原稿易容用 3 条 `dispel` 串联清除 debuff/dot/control —— 这是**事后清洗**。用户要的是**事前阻断**：挂载期间新进的负面状态直接贴不上来。引擎当前 `applyStatus`（src/combat/combat.ts）无条件接受任意状态，**没有任何"免疫/阻挡"机制**（全仓 grep 无 immune/blocks/negate 字段；本文档无 G11 小节，结论并入本 G12）。

### 改动（引擎侧）
- 新增字段 `StatusDef.immune?: StatusCategory[]`（默认 undefined）。表达"挂载此状态时，阻挡指定类别的状态被施加到该单位"。
- 在 `applyStatus` 入口处，遍历目标身上已挂载状态的 `immune` 列表，若** incoming 状态的 category 命中其中任一项**，则跳过该次施加（可记一条 log「被 immune 阻挡」）。
- `StatusCategory` 现有值需覆盖：`debuff / dot / control / buff`（C2 扩展 `dispel.category` 为数组时一起明确）；免疫字段按 category 匹配即可，不按具体 status id。
- 影响面：不止愚者，未来"净化护盾/圣盾免疫/虚化身躯"类机制都能复用 `immune` 字段。

### 状态登记（愚者·易容专用，新增）
- `disguise`（易容）：`category: buff`、`dispelable: true`、`maxStacks: 1`、`defaultDuration: 3`；`immune: [debuff, dot, control]`。
- 易容技能效果改为 `mount_status(disguise, 3t)` + `mount_status(shield, +3, 3t)`（保留原 3 点护盾）。文案从"洗掉麻烦"改为"让麻烦认不出你、贴不上身"。
- 该状态随愚者核对闭环登记于此（不进 F 组通用表）；依赖尚未实现的 G12 引擎改动。

### 改法（引擎侧，🔴 阻塞）

在单位**行动开始**节点 fire `on_turn_start`（fire 给即将行动的那个单位，语义 = "该单位自己的回合开始"）：

```ts
// 单位被调度器选中、准备执行行为前
this.fireEventTriggers(actor, 'on_turn_start', this.rootContext(actor.id));
```

注意与 `on_tick` 区分：`on_tick` 每 tick 对所有持状态单位 fire；`on_turn_start` 只在该单位轮到行动时 fire 一次（敏捷 0 约每 5 tick 一次）。

### G14-b 复核结论（好消息）

G14-b 担心的「~15 处『每回合获得 X 能量』被动」——**措辞是对的，数值也没有 5 倍通胀**。逐个核对后，它们的 hook **全部是 `on_turn_start`**（自己回合开始 ≈ 5 tick 一次），而非 `on_tick`。所以：

- 「每回合 +1/+2/+3 能量」的**措辞与数值均无需修改**。
- 真正的问题只有一个：这些技能因为 G15 而**根本不会触发**。修好 `on_turn_start` 后，G14-b 自动闭环。

### G15-b · 时间尺度冲突（状态 duration 用 tick，触发点却是 `on_turn_start`）

即使 G15 修好，下面这类写法仍然不可靠：**短 duration 状态 + 低频触发点**。

- 敏捷 0 的单位 5 tick 才出手一次，而状态 `duration: 3t` 只有 3 tick → 状态在目标轮到行动前就过期，触发器**一次都碰不到**。

已发现 2 处，处置如下：

| 位置 | 原写法 | 处置 |
|---|---|---|
| 刺客·`despair` 的 dot | `on_turn_start` 受 1 伤，`duration: 3t` | ✅ **已改为 `on_tick`**（与 `burn`/`poison`/`whisper` 一致），总量仍 3 伤（3t × 1/tick），与原文案总额一致。文档已改 |
| 囚犯·`puppet_string`（及引用它的愚者·秘偶） | `on_turn_start` 改写目标，`duration: 3t` | ⚠️ **未擅自改**（数值敏感）。两个修法：① duration 提至 ≥6t（按"目标 1 次行动"标注，敏捷越高所需 tick 越少）；② 触发改挂"单位发动攻击"的即时节点。**需拍板** |

> **设计纪律**：凡状态内触发器是 `on_turn_start`，其 `duration` 必须 ≥ 目标行动周期（建议按"N 个自身回合 × 5 tick"标注），否则改用 `on_tick`。
