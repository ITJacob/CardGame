## 5. 编队上下文（详细）

### 5.1 Unit

||||
|---|---|---|
|id|标识|战斗内唯一|
|faction|值对象|所属阵营|
|attributes|AttributeSet|配置的唯一源头（属性点）|
|baseProfile|BaseProfile|由属性点按公式派生的基础面板，战斗内不可变|
|modifiers|ModifierLayer|全部属性/资源修正的集合|
|effectiveProfile|派生（缓存）|baseProfile 应用 modifiers 后的有效值，脏时重算|
|gauges|Map|进度型资源（如行动条）|
|pools|Map|池型资源（生命 / 能量 / 护盾…）|
|statuses|StatusInstance[]|挂载中的状态|
|behaviorSlots|BehaviorSlot[]|可执行的行为（含单位级覆写）|
|skillSlots|SkillSlot[]|可用技能引用|
|channel|Channel | null|进行中的引导|
|cooldowns|Map|各行为的冷却剩余|
|position|Coordinate（只读投影）|由 Placement 单向同步，禁止其他模块写入|
|provenance|StatProvenance|本单位的属性写入溯源账本|


### 5.2 属性三层模型

AttributeSet ──公式──► BaseProfile ──┐
                                     ├──► EffectiveProfile（有效值）
   modifiers（修正集合）─────────────┘
                    ▲
                    │ 写入 / 回滚
              StatProvenance（溯源账本）

||||
|---|---|---|
|AttributeSet|战斗内不可变|属性点是配置，战斗中不改|
|BaseProfile|战斗内不可变|由属性点派生一次，缓存|
|ModifierLayer|可变|修正条目集合，每条带 sourceId|
|EffectiveProfile|派生 + 缓存|写入/回滚修正时失效缓存，下次读取重算|
|ResistanceSet|派生 + 缓存（逐元素）|每个元素一个抗性槽；基础值在 BaseProfile，增减走 ModifierLayer，按 sourceId 撤销（§8.3）|


把"修正"独立成层，是为了让任何属性都能被持续修正并按来源撤销，而不需要在属性本身里塞撤销逻辑。

抗性不是一个特殊属性：它走与攻防完全相同的三层与同一套 StatProvenance，只是按元素分槽（六个元素 → 六个槽）。这样"冰抗 -30% 持续 3 回合"和"攻击 +5"是同一种修正，撤销逻辑零新增。

### 5.3 资源：Gauge vs Pool（A2 的建模基础）

||||
|---|---|---|
|语义|累积到阈值就触发一件事|一个可以被增减的量|
|字段|current, rate, threshold, overflowPolicy|current, min, max, regen|
|变更后果|越过阈值 → 发领域事件 + 按策略扣减|数值变化；触底/触顶可发事件（如死亡）|
|典型|行动条|生命、能量、护盾|
|关键性质|是"资格"的来源|是"成本"与"状态"的载体|


Gauge.advance(tick):
    current += rate
    if current > threshold:                  // 严格大于，非等于
        emit(GaugeCrossed(unit, gauge))
        overflow = current - threshold
        current = (overflowPolicy == Keep) ? overflow : 0



"严格越过而非等于"是原设计明确的要求，此处作为不变量固定下来（见 INV-S1）。

Gauge 可被效果修改（A24）：经 modify_resource 的三个维度——gauge.current（当前进度，击退即用此键）、gauge.rate（累积速率）、gauge.threshold（触发阈值），各自带钳制下限。
⛔ 但行动周期 = threshold / rate 是派生值，禁止被 modify_stat 直接修正（INV-S5）——要改周期就改上面两个源属性之一。

### 5.4 StatProvenance 溯源账本（A6 落地）

|||
|---|---|
|apply(stat, newValue, sourceId)|写入永久修正；记录 (stat, oldValue, sourceId) 并返回句柄（remaining = null）|
|applyTimed(stat, newValue, sourceId, duration)|写入带时限修正；条目自带 remaining，由 tick 递减，到期自动 revertBySource（A21）|
|revertBySource(sourceId)|按来源回滚全部条目（状态到期 / 被驱散 / 光环移除 / 时限耗尽 / 单位离场时调用）|
|revertAll()|清空本单位全部修正（单位离场）|
|entriesOf(stat)|审计视图：某项属性的全部修正来源|


不变量
- INV-P1：每个 sourceId 在单位上全局唯一（不是状态类型 ID，是实例 ID）。
- INV-P2：revertBySource 必须把属性恢复到该来源写入前的值，而非"减去写入量"（多条修正叠加时二者不同）。
- INV-P3：账本条目与 ModifierLayer 的修正条目一一对应，不存在无主修正。
- INV-P4：单位离场时 revertAll() 必须被调用（否则修正泄漏到对象池复用时）。
- INV-P7：dispel 只作用于 StatusInstance；modify_stat 写入的属性修正不可被驱散，只按 duration 到期回滚（A21）。


A6 修正确认：溯源键是 StatusInstanceId。同种状态的两个实例各自记账、各自撤销，互不干扰。

### 5.5 状态三件套（A7 落地）

||||
|---|---|---|---|
|内容|id, category、触发表 TriggerDef[]、行为约束算子 BehaviorModifier[]、转向声明 RedirectRule、defaultDuration、maxStacks、stackPolicy、dispelable|duration、stacks、强度参数 params、sourceId、特殊绑定 binding（守护目标 / 转移目标）|instanceId、defId、grant 副本、remaining、currentStacks、已解析绑定|


挂载流程（含叠加）

mount(defId, grant):
    existing ← 找本单位同 defId 的 Instance
    if existing == null:
        inst ← new StatusInstance(instanceId = newId(), defId, grant)
        inst.remaining ← clamp(grant.duration ?? def.defaultDuration, 0, 上限)
        inst.currentStacks ← clamp(grant.stacks ?? 1, 1, def.maxStacks)
    else:
        if existing.currentStacks < def.maxStacks:
            existing.currentStacks += grant.stacks
        existing.remaining ← max(existing.remaining, grant.duration)   // stackPolicy = refresh
    emit(StatusMounted | StatusRefreshed)
    触发 def.triggers 中 event == on_apply 的条目（产出 Action）

销毁流程（含撤销）

unmount(instanceId, reason):     // reason: Expired | Dispelled | UnitLeft | Consumed
    触发 def.triggers 中 event == on_remove 的条目（若定义）
    provenance.revertBySource(instanceId)      // INV-P2
    移除 instance
    emit(StatusExpired | StatusDispelled)

状态对战斗的两类贡献（沿用 v1.3 已确认的划分，此处落到模型）

|||
|---|---|---|
|(a) 触发型|事件命中 → 产出 Action → 走流水线|StatusDef.triggers|
|(b) 声明式约束|挂载期间被流水线特定节点被动读取，不是 Action|BehaviorModifier → 流水线前；RedirectRule → R 节点|


二者正交，一个状态可同时携带。

### 5.9 攻击类型（reach）与目标可达性（v1.1 新增）

#### 5.9.1 核心澄清：站位 / reach / 目标选择 三者正交

||||
|---|---|---|---|
|Coordinate（站位）|战场|单位在队列中的物理位置|与攻击方式无关|
|reach（近战 / 远程）|攻击类行为的属性|① 是否触发同步对撞 ② 是否可被拦截|不决定能打哪些坐标|
|targetSpec|行为的属性|能选哪些坐标（含排序与选择模式）|与攻击方式无关|


这是本次补充最重要的一条：近战 ≠ 只能打前线。
"近战"描述的是交战方式（贴身互搏、双方同时受伤）；"打哪个坐标"由 targetSpec 独立决定。
因此刺客「越过最前一个单位打其后方单位，且算近战伤害」是自然成立的组合——只需在该行为的 targetSpec 里用 absolute + fixedIndex 指定目标坐标，reach 仍为 Melee，越位攻击照样触发对撞。不需要新增任何机制。

#### 5.9.2 reach 的语义

||||
|---|---|---|---|
|Melee|✅ 目标对攻击者同时造成伤害|否（直接交锋）|战士普攻、刺客越位突袭|
|Ranged|❌ 攻击者不受伤害|✅ 可被守卫姿态承接|远程普攻、投射类技能|
|None|—|—|非攻击类行为（加甲、治疗、召唤…）|


#### 5.9.3 守卫姿态：RedirectRule 的扩展

守卫战士"承接所有针对其身后单位的远程伤害"——这是 RedirectRule 的一个实例，但需要两处扩展：

RedirectRule {
    op     : redirect
    to     : self | attacker | transfer_target
    protectedSelector:                          // 【新增】受保护目标的选择器
        | { kind: UnitRef, unitId }             //   保护指定单位（原「守护」）
        | { kind: CoordinateRelation, relation }// 【新增】按坐标关系动态确定（守卫姿态）
    sourceFilter: Melee | Ranged | Skill | Any  // 【新增】只拦截特定来源
    ratio   : float
    priority: int
}

|||
|---|---|---|
|受保护对象|一个指定单位|同路且 index 大于自己的全部单位（坐标关系）|
|拦截来源|全部|仅远程（sourceFilter: Ranged）|
|本质|同一个 RedirectRule，只是选择器与来源过滤不同||


两个能力因此统一为一条机制，不必为"守卫"另造一套拦截系统。

#### 5.9.4 stance 状态分类与「硬控清除姿态」

守卫姿态是一种状态（挂在单位上、有持续时间、可被移除）。新增分类与规则：

|||
|---|---|
|StatusDef.category 新增取值|stance（姿态）|
|语义|姿态 = 单位主动维持的一种交战状态|
|硬控规则|硬控（stun）命中时，清除目标身上的全部 stance 状态|


设计要点：用「分类驱动」批量行为，而不是在眩晕里枚举要清除哪些状态。

|||
|---|---|
|眩晕定义不变，新增姿态自动被清除|每加一种姿态都要回头改眩晕配置|
|语义清晰："硬控打断一切姿态"|易漏配；漏配表现为玄学 bug|


## 6. 调度上下文（详细）

### 6.1 BattleClock 与 Tick

tick():                                   // 一个原子步
    1. clock.advance()
    2. 所有 Unit 的 Gauge.advance()        // 可能发 GaugeCrossed
    3. 所有 Pool 按 regen 恢复
    4. Channel.remaining--
    5. Cooldown.remaining--
    6. StatusInstance.remaining--（到期者 unmount）；**StatProvenance 带时限条目 remaining--（到期者 revertBySource）**   // A21
    7. Zone 的 duration 递减（到期者移除）
    8. 收集本 tick 内所有 GaugeCrossed → 交由 InitiativePolicy 排序 → 依次授予机会

顺序纪律：推进（1–7）与授予（8）严格分离——先把世界推进到稳定态，再决定谁行动。否则会出现"单位 A 行动时，B 的资源还没恢复"这种依赖 tick 内顺序的隐蔽 bug。

### 6.2 ActionOpportunity（A2 落地）

|||
|---|---|
|unitId|获得者|
|tickIndex|授予时刻|
|consumedBy|被哪个 Action 消耗（未消耗则记录为 wasted）|


两条独立校验（这是拆分的核心收益）

|||
|---|---|---|
|资格校验：是否持有未消耗的机会|调度|不能执行主动行为|
|成本校验：Gauge 扣减量 + Pool 是否足够|编队|行为不可选（进不了可选列表）|


commit(behavior):
    assert opportunity != null and !opportunity.consumed      // 资格
    assert cost.payable(unit)                                  // 成本
    unit.gauge.consume(cost.gaugeAmount)
    unit.pools.consume(cost.energyAmount)
    opportunity.consumedBy ← new Action
    → 进入执行流水线

默认纪律：cost.gaugeAmount = threshold（扣满阈值进度条），任何偏离需平衡评审。

#### 6.2.3 关于眩晕语义（A2′，标记为可选）

现状：眩晕 = 精力恢复归零（用资源手段模拟资格剥夺）。
拆出 ActionOpportunity 后，可直接表达为「剥夺 N 次机会」，语义更准。

但本版不改，原因：
1. 二者在当前数值下是否等价需要重新验证（归零期间还影响"越界留存"的累积）；
2. 改动会牵动平衡文档与验证脚本。

建议：保持现状实现，在参数层把"眩晕"标注为待重评项，等骨架落地后用新版验证脚本对比两种实现的 TTK 差异再决定。

### 6.3 InitiativePolicy（先手）

契约：输入本 tick 内全部 GaugeCrossed，输出确定性的行动序列。

resolveOrder(crossed):
    己方序列 ← sort(crossed.where(己方), by (lane, index))
    敌方序列 ← sort(crossed.where(敌方), by (lane, index))
    return 交替合并(己方序列, 敌方序列)     // 按既定交替模式

不变量
- INV-S1：Gauge 触发条件为严格越过阈值（>，非 ≥）。
- INV-S2：序列必须按双方各自排序后交替合并得出，不得按战场位置分层合并。
  > 原设计踩过这个坑：初版按 index 分层实现，给分兵方不公平先手（22:14），修正为交替合并后对称性恢复。此处固化为不变量，防止回归。
- INV-S3：同 tick 内每个单位至多获得一次机会。
- INV-S4：机会未被消耗（如无可用行为）时，明确记为 wasted，不累积到下一 tick。

### 6.4 OpportunityFilter（可选行为列表）

availableBehaviors(unit):
    unit.behaviorSlots
      .where(b => b.trigger == Active)
      .where(b => !b.isRedirectDisabled)        // 决策期约束：disable
      .where(b => force 集合为空 or b ∈ force)   // 决策期约束：force
      .where(b => b.cooldownRemaining == 0)
      .where(b => unit.channel == null)
      .where(b => cost.payable(unit))           // 含 energy_cost_mul / add 修正后的最终成本

过滤顺序固定，结果确定。

## 7. 执行上下文（详细）

### 7.1 ActionSource 薄接口（A5 落地）

ActionSource {
    ignition    : Commit(消耗机会+扣资源) | EventTrigger(不消耗)
    targetSpec  : TargetSpec | null
    effects     : EffectRef[]
}

|||
|---|---|---|
|BehaviorSlot（主动）|Commit|玩家/AI 选定|
|BehaviorSlot（被动）|EventTrigger|绑定 passiveHook 事件|
|StatusInstance|EventTrigger|StatusDef.triggers 命中|


三者不共享生命周期管理，只共享这个契约与产物类型（Action）。未来加装备/地形/光环触发，流水线零改动。

### 7.2 Action 实体

|||
|---|---|---|
|id|不可变|唯一标识|
|sourceRef|不可变|来源（行为实例 / 状态实例 / 技能定义）|
|caster|不可变|施法方快照|
|opportunityId|不可变|消耗的机会（EventTrigger 时为 null）|
|committedTargets|不可变快照|I 节点产出，此后不再修改|
|behaviorContext|不可变|决策期约束聚合结果|
|finalTargets|增量写入|R 节点产出|
|redirectLog|追加|每次转向的审计|
|settlementPlan|增量写入|逐最终目标的结算计划|
|consumption|不可变|instant / zone / summon|
|outcomes|追加|每个效果的落地结果|


核心纪律：committedTargets 是干净快照，动作期干预只能在它之上做增量改写，绝不回写。决策期与动作期因此物理隔离。

### 7.3 流水线四节点契约

||||||
|---|---|---|---|---|
|I 目标解释|caster + targetSpec|committedTargets: ResolvedTarget[]|战场坐标空间、施法方状态|可被 target_override 覆盖 request|
|R 动作期干预|committedTargets|finalTargets + settlementPlan + redirectLog|目标方及其友军的状态|目标归属 + 结算计划|
|M 消费分流|finalTargets + consumption|三条路径之一|—|无|
|O 结果应用|路径 + effects|outcomes + 领域事件|每条效果的 condition|单位/战场状态|


#### I 节点（v1.1：拆为「候选池 → 收缩」两段）

I-1 · 候选池

1. 解析 targetSpec.request 中的上下文相关项（如 laneRef 的"自动"）→ 具体值   // 见 B3
2. 按 faction 确定扫描阵营；按 laneRef 确定扫描路线
3. 按 anchor 解析锚点坐标；按 scope 圈定候选坐标
4. 每个坐标附当前 occupant 快照 → ResolvedTarget{coord, occupant}
5. 产出 CandidatePool { targets, stateVersion, pickCount, selectionMode, fallbackSort }

I-2 · 收缩（依据 selectionMode）

|||
|---|---|
|Auto|按 sort 排序 → 截 pickCount → committedTargets|
|Manual|候选数 ≤ pickCount → 全取，不打断玩家候选数 > pickCount → 等待玩家选择输入；无玩家在场时走 fallbackSort|


- 产出物是坐标，occupant 仅是该坐标在结算时刻的租客，可以为 null（空坐标是合法目标——召唤依赖此）。
- 候选为空时返回空集合，上层跳过而非抛异常（原已拍板）。
- stateVersion 用于提交时校验战场是否发生变动（INV-E6）。



A9 的确定性兜底：Manual 模式的 fallbackSort 必填。
原因：状态触发与被动行为产生的 Action 没有玩家在场（自动点火）。若此时遇到 Manual 目标规格且无兜底，结果将依赖未定义行为——直接违反 B1 铁律。
fallbackSort 同时服务三种场景：AI 决策 / 状态与被动触发 / 网络对战超时。

附带的一条交互纪律：候选数 ≤ pickCount 时不弹选择。避免出现"只有唯一合法目标还要玩家点一下"的无效交互。

#### R 节点（B2 落地）

职责明确为：解析转向 + 生成逐目标结算计划。它不执行结算。

for each original in committedTargets:
    candidates ← 收集 original 自身的 RedirectRule
               ∪ 收集其存活友军中 guardTarget == original 的 RedirectRule

### 7.5 近战同步对撞（v1.1 新增）


规则：近战类攻击结算时，双方在那一刻彼此同时造成伤害（被攻击者未丧失还击能力的前提下）。

#### 7.5.1 建模为「反作用动作」，而不是给每个单位配被动

把它做成"所有单位默认配置一个还击被动"也可以，但那样每个单位都要配、每个新单位都要记得配，漏配就是玄学 bug。

更好的做法：建模为引擎级结算规则，但复用 ActionSource 抽象产出一个同型的 Action：

MeleeClash（反作用动作）
    sourceRef  : melee_clash
    ignition   : EventTrigger        // 不消耗行动机会、不消耗资源
    targetSpec : { faction: attacker }   // 目标 = 攻击来源
    effects    : 由结算规则给出（走同一条伤害链）

|||
|---|---|
|复用流水线|对撞伤害走完整 I→R→M→O，自动获得转向、减伤、条件过滤|
|可被状态干预|眩晕 disable 掉还击能力 → 自动不触发对撞（无需特判）|
|审计可见|Action 带 sourceRef = melee_clash，回放可区分|
|防环|on_take_damage 不再二次触发（INV-E4 已覆盖）|


#### 7.5.2 触发条件

触发对撞 ⟺
    行为.reach == Melee
  ∧ 主目标存在且存活
  ∧ 主目标未被剥夺还击能力（眩晕 / 同类硬控）
  ∧ 主目标够得着攻击者 —— **B7 已裁定：首批不校验**（扩展点保留）


✅ B7 已拍板：首批不校验可达性，近战一律对撞。
理由——规则简单、玩家可预期、实现成本低。可达性校验作为扩展点保留，等实测发现"越位刺客无脑白嫖"再补。

#### 7.5.3 「同步」的执行语义（关键）

1. 主结算：  计算 caster → target 的伤害结果（纯函数，不改状态）
2. 对撞结算：计算 target → caster 的伤害结果（纯函数，不改状态）
3. 同时应用两条结果


不变量 INV-E7：对撞不能中断主攻击。
即使第 2 步算出攻击者会被对撞致死，第 1 步的伤害仍然结算——因为二者发生在同一刻。这是"同步"一词的实际含义，也是它与"先攻后反击"的根本区别。

|||
|---|---|---|
|攻击者被对撞致死|主伤害仍生效|主伤害可能不生效|
|玩家可预期性|高（稳定换血）|低（依赖结算顺序）|
|与眩晕的交互|眩晕 → 不还击|同|


#### 7.5.4 与既有机制的关系

|||
|---|---|
|反伤（thorns）|并行不冲突：反伤是状态触发的额外伤害，对撞是近战固有还击；二者可叠加，且都不二次触发 on_take_damage|
|伤害转移 / 守护 / 守卫姿态|对撞伤害同样走 R 节点，可被转向（守护者可能替攻击者扛下对撞）|
|INV-D4（状态伤害不进通用乘区）|对撞是行为伤害，不是状态伤害 → 正常进入通用乘区|
